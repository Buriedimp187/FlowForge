read-only architecture/correctness review conducted before any M2 code was written.
It is the **how**; `docs/architecture.md` sections 3–6.2a remain the **what**

## 1. Tooling decisions (D1–D3)

| # | Decision | Resolution |
|---|---|---|
| D1 | Primary-key / ID generation | **UUIDv7, generated by the application via Python 3.14's native `uuid.uuid7()`.** No added dependency, no database-side default, no reliance on any PostgreSQL-18-only feature. Verified directly against `docs.python.org/3.14/library/uuid.html`: `uuid7()` was added in 3.14 (RFC 9562 §5.7), takes no arguments, embeds a 48-bit millisecond timestamp plus a 42-bit counter guaranteeing monotonicity within a millisecond. Schema PK columns carry no `DEFAULT`; every INSERT site supplies the id explicitly (`id = uuid.uuid7()`, generated in Python before the statement executes). psycopg 3 adapts `uuid.UUID` to Postgres's native `uuid` type automatically. UUIDv7 over UUIDv4 is adopted purely for B-tree insert locality (new rows cluster near the index's high end instead of scattering randomly) — explicitly **not** for "avoiding sequence contention" (there was never a sequence in this design) and with no correctness dependency anywhere on ID ordering (claim order uses `visible_at`; fencing uses `lease_epoch`; finalization precedence uses `status`). |
| D2 | Database access layer | **SQLAlchemy Core (`Connection`, `text()`) for connection/transaction management; explicit, literal SQL for all T0–T4 operations; `psycopg3` as the driver (`postgresql+psycopg` dialect); Alembic for migrations. No ORM.** No concrete requirement for an ORM was found anywhere in M2's scope — the five hot-path statements are, by design, meant to stay literal and auditable exactly as specified in `docs/architecture.md` §4–§6.2a. Confirmed: Core's `text()` passes SQL through essentially verbatim (locking clauses, `CASE` expressions, partial indexes all untouched); `engine.begin()`/`Connection.begin()` map directly onto the `BEGIN...COMMIT` blocks already specified; bound parameters are sent to the driver as real parameters, never string-interpolated. **One implementation rule adopted from this review:** avoid `::cast` syntax inside `text()` blocks (ambiguous with SQLAlchemy's `:name` bind-parameter scanning in some contexts) — use `CASE WHEN ... THEN 1 ELSE 0 END` or `CAST(x AS type)` instead; see the claim SQL in section 4.2. |
| D3 | Real-PostgreSQL test infrastructure | **No Dockerfile or Compose file before M4** (preserving `docs/milestones.md`'s literal "the first Dockerfiles and Compose files are created [at M4]"). Local/dev integration tests use `testcontainers-python` (spins up the official `postgres:17` image imperatively from test code — no Dockerfile/Compose artifact ever lands in the repository). CI adds PostgreSQL via GitHub Actions' native `services:` block in a **new job in the existing `.github/workflows/ci.yml`** (confirmed to fit: the workflow already runs on `ubuntu-latest`, pins third-party actions by commit SHA per ADR-0015, and its own header comment states it is "designed to be extended, not replaced"). The `postgres` service image should be digest-pinned, consistent with the project's existing no-floating-tags discipline. `testcontainers[postgres]` is a backend **dev/test-only** dependency, never a runtime dependency of the shipped application. |

## 2. Database schema

Exactly five tables for M2 — `workflows` and `workflow_versions` exist only so
`runs.workflow_version_id` has a legitimate FK target; M2 does not implement
workflow CRUD, authentication, credentials, or webhook ingress (M4's scope).
`admin_user`, `sessions`, `credentials`, `webhook_endpoints`, `app_settings` are
deliberately **not** created by M2's migration.

```sql
CREATE TABLE workflows (
    id              uuid PRIMARY KEY,                   -- app-generated uuid7(), no DEFAULT
    name            text NOT NULL,
    active_version_id uuid,
    webhook_enabled boolean NOT NULL DEFAULT false,
    created_at      timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE workflow_versions (
    id              uuid PRIMARY KEY,                   -- app-generated uuid7()
    workflow_id     uuid NOT NULL REFERENCES workflows(id),
    version_number  integer NOT NULL,
    schema_version  integer NOT NULL,
    definition      jsonb NOT NULL,                      -- immutable once written
    created_at      timestamptz NOT NULL DEFAULT now(),
    UNIQUE (workflow_id, version_number),
    UNIQUE (workflow_id, id)                              -- required target for the composite FK below
);

-- Active-version integrity: the active version must belong to its OWN
-- workflow, not merely exist somewhere in workflow_versions.
ALTER TABLE workflows ADD CONSTRAINT fk_active_version_belongs_to_workflow
    FOREIGN KEY (id, active_version_id) REFERENCES workflow_versions (workflow_id, id);
    -- NULL active_version_id (a brand-new workflow) trivially satisfies this
    -- under Postgres's default MATCH SIMPLE.

CREATE TABLE runs (
    id                  uuid PRIMARY KEY,                -- app-generated uuid7()
    workflow_version_id uuid NOT NULL REFERENCES workflow_versions(id),
    status              text NOT NULL
        CHECK (status IN ('queued','waiting','running',
                           'succeeded','failed','cancelled','timed_out')),
    visible_at          timestamptz NOT NULL,
    lease_owner         text,
    lease_epoch         bigint NOT NULL DEFAULT 0 CHECK (lease_epoch >= 0),
    recovery_count      integer NOT NULL DEFAULT 0,
    cancel_requested_at timestamptz,
    queue_deadline_at   timestamptz NOT NULL,
    deadline_at         timestamptz,
    started_at          timestamptz,
    finished_at         timestamptz,
    error               jsonb,
    has_unknown_outcome boolean NOT NULL DEFAULT false,
    trigger_payload     jsonb NOT NULL,
    idempotency_key     text,
    created_at          timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT lease_owner_matches_status CHECK (
        (status = 'running' AND lease_owner IS NOT NULL) OR
        (status <> 'running' AND lease_owner IS NULL)
    ),
    UNIQUE (workflow_version_id, idempotency_key)        -- NULLs don't collide
);

-- Serves claim, reclaim, and park-wakeup uniformly; terminal runs fall out
-- of it automatically (architecture.md section 4.1).
CREATE INDEX runs_claimable_idx ON runs (visible_at)
    WHERE status IN ('queued','waiting','running');

CREATE TABLE node_runs (
    run_id         uuid NOT NULL REFERENCES runs(id),
    node_key       text NOT NULL,
    status         text NOT NULL
        CHECK (status IN ('running','retry_wait','succeeded','failed','skipped','cancelled')),
    attempt        integer NOT NULL DEFAULT 1,
    failures       integer NOT NULL DEFAULT 0,
    outcome        text NOT NULL DEFAULT 'known' CHECK (outcome IN ('known','unknown')),
    effect_class   text CHECK (effect_class IN ('pure','read','idempotent_write','unsafe_write')),
    started_epoch  bigint,            -- the lease_epoch active at this row's last T2
    started_at     timestamptz,
    retry_at       timestamptz,       -- always DB-computed (now() + interval), never worker-computed
    resolved_params jsonb,
    output         jsonb,
    error          jsonb,
    item_results   jsonb,
    PRIMARY KEY (run_id, node_key),
    CHECK (status = 'skipped' OR effect_class IS NOT NULL),
    CONSTRAINT retry_wait_requires_retry_at
        CHECK (status <> 'retry_wait' OR retry_at IS NOT NULL)
);

CREATE FUNCTION enforce_effect_class_immutable() RETURNS trigger AS $$
BEGIN
    IF NEW.effect_class IS DISTINCT FROM OLD.effect_class THEN
        RAISE EXCEPTION 'effect_class is immutable for (run_id=%, node_key=%): % -> %',
            OLD.run_id, OLD.node_key, OLD.effect_class, NEW.effect_class;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER node_runs_effect_class_immutable
    BEFORE UPDATE ON node_runs
    FOR EACH ROW EXECUTE FUNCTION enforce_effect_class_immutable();

CREATE TABLE run_events (
    run_id    uuid NOT NULL REFERENCES runs(id),
    seq       bigint NOT NULL,
    level     text NOT NULL CHECK (level IN ('debug','info','warning','error')),
    node_key  text,
    message   text NOT NULL,          -- pre-redacted before insert (architecture.md section 10)
    ts        timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (run_id, seq)
);
```

## 3. Worker authorization objects

Two distinct objects, with distinct lifetimes — conflating them was an error caught
and corrected during this review, and the distinction is load-bearing:

```python
@dataclass(frozen=True)
class ClaimedRun:
    """Durable record of this worker's belief that it owns a run, as of the
    last successful T1 claim/reclaim. Survives across every subsequent
    transaction (heartbeat, T2, T3, park, T4) for the entire lifetime of
    this worker's engagement with the run.

    Grants NO write authorization by itself. Every later operation must
    re-verify (lease_owner, lease_epoch) against the database fresh, via
    run_fenced_guard(); the epoch cached here is used only as that
    re-check's PARAMETER, never as a substitute for it.

    prev_status is the run's status as locked by T1 before the claim
    ('queued' | 'waiting' | 'running'); post-claim check 1 needs it (checks 1-2
    read the first fenced guard's db_now, so no claim-time timestamp is kept)."""
    run_id: str
    lease_owner: str
    lease_epoch: int
    deadline_at: datetime
    queue_deadline_at: datetime
    recovery_count: int
    prev_status: str


@dataclass(frozen=True)
class LeaseProof:
    """Authorization bound to its issuing Connection and the currently
    active ROOT transaction, valid for as long as that root transaction
    remains open (not committed, not rolled back, connection not closed).
    May be presented to any number of protected writes (append_event,
    etc.) within that same root transaction -- it is not single-use or
    consumed on first use.

    The fenced UPDATE that produced this proof, and the row lock it took,
    live in that root transaction. A savepoint opened and later closed
    (committed or rolled back) within it -- before or after this proof
    was created -- does not retroactively invalidate it: a savepoint can
    only undo work performed after it was established, so it cannot undo
    a fenced write that already happened earlier in the same root
    transaction. This proof's type does NOT track "a savepoint was ever
    opened during my lifetime" -- no such state exists, and none is
    needed. What actually matters is narrower and is enforced live, at
    the moment each protected operation acts: run_fenced_guard(),
    append_event(), and claim_run() each check, via
    _reject_if_nested(), whether a nested transaction is open RIGHT NOW,
    and refuse if so -- this is what prevents a protected write from
    ever executing while a still-open savepoint could later undo it. Do
    not describe this proof as "becoming invalid the instant a savepoint
    is opened" -- that is not what is implemented or needed; only an
    actively-open nested transaction at the moment of a check is
    rejected.

    This is an INTERNAL CORRECTNESS GUARD against the worker's own
    orchestration code accidentally reusing a stale reference -- NOT a
    security boundary. @dataclass(frozen=True) and a leading underscore
    do not prevent other code in the same process from constructing a
    LeaseProof by hand, bypassing run_fenced_guard()/claim_run() entirely;
    Python has no sealed-constructor mechanism. The real, DB-enforced
    protection for node_runs/runs is the row lock and the WHERE
    lease_owner=.../lease_epoch=... predicate on the SQL itself, which
    does not consult this object at all. run_events specifically relies
    on this object being honestly obtained -- accepted as a deliberate,
    disclosed limitation, since M2 has no adversarial-code threat model
    (node execute() is first-party; no eval, no arbitrary code
    execution anywhere in this project)."""
    run_id: str
    lease_owner: str
    lease_epoch: int
    _conn: "Connection"
    _txn: object            # identity of conn.get_transaction() at creation


@dataclass(frozen=True)
class FencedGuardResult:
    """Pairs a LeaseProof with the business-data columns a caller needs
    from the same RETURNING clause, without putting business data on the
    (deliberately minimal) proof itself. db_now is a fresh reading of the
    database clock: the single clock_timestamp() sample that also stamps the
    lease renewal (returned as visible_at - ttl) -- NOT the transaction-start
    now() -- callers compare
    deadline_at against THIS value, never against their own local clock
    (docs/architecture.md section 4: "All timestamps are the database
    clock... never a worker's local clock")."""
    proof: LeaseProof
    cancel_requested_at: Optional[datetime]
    deadline_at: datetime
    db_now: datetime
```

**Guard timestamp and lease renewal (`clock_timestamp()`).** `run_fenced_guard()`
stamps the lease from a fresh database-clock sample and returns that **same**
sample as `db_now`:

```sql
UPDATE runs SET visible_at = clock_timestamp() + :ttl
 WHERE id = :run_id AND status = 'running'
   AND lease_owner = :worker AND lease_epoch = :epoch     -- authorization: NO visible_at here
RETURNING lease_owner, lease_epoch, cancel_requested_at, deadline_at,
          visible_at - :ttl AS db_now                      -- the renewal's own sample, not a second clock call
```

PostgreSQL's `now()` is the *transaction start* time, so the previous
`visible_at = now() + :ttl` stamped a stale expiry whenever the guard waited on the
`runs` row lock: a guard that waited `W` seconds behind a long writer renewed the
lease to `fresh + ttl − W`. Using `clock_timestamp()` removes that, and deriving
`db_now` as `visible_at − :ttl` guarantees renewal and reading are one instant.

**What is documented, what is tested, and what is not claimed.** PostgreSQL 17's
documentation states that `clock_timestamp()` "returns the actual current time, and
therefore its value changes even within a single SQL statement", that `now()` is
the transaction start, that row-level locks "are released at transaction end", and
that under READ COMMITTED a blocked `UPDATE` waits and then re-evaluates its
`WHERE` condition on the updated row version. It does **not** document when a
`SET` expression is evaluated relative to the row lock, nor that `SET` expressions
are re-evaluated after a wait. This design therefore claims only this: when the
blocker committed a *new row version* of `runs` — which every writer in this
design does (guard, T1, T4, API cancel) — the executor recomputes the new tuple
after the wait and the sample is post-wait; that behavior is pinned by a real-
PostgreSQL test (§9, (cc)), not assumed. A blocker that releases the lock *without*
modifying the row (for example a rolled-back claim) could leave a sample taken
before the wait: at most `W` **earlier**, never later than a fresh reading.

**Why this is safe under the row-lock and epoch-fencing protocol.**

1. *Authorization is unchanged.* The `WHERE` predicate is still `status`,
   `lease_owner`, `lease_epoch`; `visible_at` is **not** added to it. No lease
   validity decision may be based on `visible_at > now()` alone: expiry does not
   revoke ownership until a new claimant actually increments `lease_epoch` (§3.1,
   "Why `visible_at` does not appear…").
2. *A fresher stamp cannot extend or resurrect a lease.* A reclaim that committed
   before this guard obtained the lock makes the `WHERE` fail (0 rows): **no**
   renewal is written. If the guard holds the lock, T1's `SKIP LOCKED` passes over
   the row, so no reclaim can interleave; after commit `visible_at` is about `ttl`
   in the future, so there is no immediate reclaim.
3. *The worst case is conservative.* In the lock-only-blocker case above the expiry
   is stamped up to `W` early (ms against a 30 s TTL): a competing claimant could
   enter at most `W` sooner, and epoch fencing then supersedes the old holder as it
   always does — the same outcome as a worker slowed by `W`, which the dedicated
   heartbeat design (R3) already tolerates.
4. *T1 and T2 are unchanged.* T1's `visible_at = now() + :ttl` is unchanged because
   T1 never waits (`SKIP LOCKED`, and its `UPDATE` targets a row its own `SELECT`
   already locked). T2's `retry_at <= now()` is unchanged: `now()` being the
   transaction start can only delay a retry, which is conservative.

**What the guard's timestamp is used for, and what it is not.**

- **T4 still independently checks the deadline** atomically in its own statement
  (§4.5, term 1, on one `clock_timestamp()` sample). The guard's timestamp feeds the
  loop's *earlier-stage* decisions only (below); it is never an input to T4.
- **No Python-side timestamp can replace the T4 deadline predicate.** `db_now`,
  a monotonic timer, and the in-memory `deadline_confirmed` flag are
  hints or earlier-stage decisions; the finalizing decision is made inside the
  statement that commits it.

*Every use of the returned timestamp, and the effect of this change:*

| Use | Where | Effect of the change |
|---|---|---|
| `guard.deadline_at <= guard.db_now` at T2 | §4.3, §8 row 17 | Fresher by at most the lock wait; expiry is detected no later than before; no semantic change |
| Same comparison for `deadline_confirmed` after the fresh guard | §4.7 step 5, §4.8 item 2, §4.9 item 1 | Same |
| Arming/re-arming the timer: `remaining = deadline_at - db_now` | §4.8 items 1 and 4 | A slightly more accurate estimate; an early or late fire is still re-checked by a fresh guard, so correctness is unchanged |
| Post-claim checks 1–2 (first guard's `db_now`) | §4.2 | Same comparison as above, evaluated on the first fenced guard after the claim |
| The lease renewal itself | §3.1 (this statement) | **Changed on purpose:** stamped from the fresh sample instead of the transaction start; authorization predicate untouched |
| T1's `visible_at = now() + :ttl` | §3.1 `claim_run()` | **Unchanged** — T1 never waits |
| T2's due-retry predicate `retry_at <= now()` | §4.3 | **Unchanged** — conservative, not a deadline decision |
| T4's deadline term and `finished_at` | §4.5 | Independent; one `clock_timestamp()` sample, never the guard's value |

**Nested transactions/savepoints are prohibited in the worker persistence layer**:
protected operations reject an actively-open nested transaction at the moment
they execute. Verified directly against SQLAlchemy 2.x's documented API
(`docs.sqlalchemy.org/en/20/core/connections.html`): `Connection.get_transaction()`
returns the **root** transaction only; a `SAVEPOINT` opened via `begin_nested()`
is a separate `NestedTransaction` object, and opening or rolling one back does
**not** change what `get_transaction()` returns. The actual, narrow hazard this
guards against: if a protected write (the fenced `UPDATE`, or an `append_event()`
insert) were allowed to execute **while** a savepoint is open, a later rollback
to that savepoint could undo it — so each protected operation checks, live,
whether it is currently nested and refuses if so, rather than trusting any
root-transaction-identity check alone to catch this (it would not, since root
identity is unaffected by a savepoint either way). A savepoint opened and
already closed before or after a given check is not something this mechanism
tracks or needs to track — see the `LeaseProof` docstring above for the precise,
narrower contract. Resolution: reject outright, at both issue and check sites,
since nothing in M2's design anywhere needs a savepoint:

```python
def _reject_if_nested(conn: Connection) -> None:
    if conn.get_nested_transaction() is not None:
        raise RuntimeError(
            "a SAVEPOINT is active on this connection -- protected "
            "operations (run_fenced_guard, claim_run, append_event) "
            "do not support nested transactions in this layer"
        )

def _check_proof(conn: Connection, proof: LeaseProof) -> None:
    _reject_if_nested(conn)
    if conn is not proof._conn:
        raise RuntimeError("LeaseProof presented on a different connection than issued it")
    if conn.get_transaction() is not proof._txn:
        raise RuntimeError("LeaseProof is stale: its transaction has ended, or a new "
                            "one has begun on this connection since")
```

If a genuine future need for nested transactions arises, the correct extension is
binding proofs to the complete transaction context (root **and** nested) rather
than lifting this prohibition casually — not built now, since there is no concrete
need for it.

### 3.1 Core operations

```python
def claim_run(conn, worker: str, ttl: int, run_timeout: int) -> Optional[ClaimedRun]:
    with conn.begin():
        row = conn.execute(text("""
            SELECT id, status AS prev_status FROM runs
             WHERE status IN ('queued','waiting','running') AND visible_at <= now()
             ORDER BY visible_at LIMIT 1
             FOR UPDATE SKIP LOCKED
        """)).fetchone()
        if row is None:
            return None

        claimed = conn.execute(text("""
            UPDATE runs SET
               status = 'running', lease_owner = :worker,
               lease_epoch = lease_epoch + 1,
               recovery_count = recovery_count + CASE WHEN status = 'running' THEN 1 ELSE 0 END,
               visible_at  = now() + :ttl,
               started_at  = COALESCE(started_at, now()),
               deadline_at = COALESCE(deadline_at, now() + :run_timeout)
             WHERE id = :id
            RETURNING lease_epoch, recovery_count, cancel_requested_at,
                      deadline_at, queue_deadline_at
        """), {"id": row.id, "worker": worker, "ttl": ttl, "run_timeout": run_timeout}).fetchone()

        # NOT `claimed.recovery_count > 0`: recovery_count is cumulative for
        # the whole life of the run, so it stays positive on every later
        # ordinary claim (e.g. an ordinary wake-from-`waiting` after a prior
        # park) once it has ever been incremented once -- that would log a
        # spurious "reclaimed" event on every such later claim, not just the
        # one that actually reclaimed an abandoned lease. The correct,
        # reliable signal is `prev_status`, captured from the row as locked
        # by the SELECT above, BEFORE this UPDATE applied -- the exact same
        # condition the UPDATE's own `recovery_count` CASE expression tests
        # (`status = 'running'` there reads the pre-UPDATE value, provably
        # identical to `prev_status`). recovery_count's own increment
        # semantics are unchanged by this correction.
        if row.prev_status == "running":
            # Transaction-local proof, used once, discarded when this
            # `with` block exits -- never returned, never stored.
            proof = LeaseProof(row.id, worker, claimed.lease_epoch, conn, conn.get_transaction())
            append_event(conn, proof, "info", None,
                         f"run reclaimed (recovery_count={claimed.recovery_count})")

    return ClaimedRun(
        run_id=row.id, lease_owner=worker, lease_epoch=claimed.lease_epoch,
        deadline_at=claimed.deadline_at, queue_deadline_at=claimed.queue_deadline_at,
        recovery_count=claimed.recovery_count, prev_status=row.prev_status,
    )


def run_fenced_guard(conn, claimed: ClaimedRun, ttl: int) -> Optional[FencedGuardResult]:
    _reject_if_nested(conn)
    row = conn.execute(text("""
        UPDATE runs SET visible_at = clock_timestamp() + :ttl
         WHERE id = :run_id AND status = 'running'
           AND lease_owner = :worker AND lease_epoch = :epoch
        RETURNING lease_owner, lease_epoch, cancel_requested_at, deadline_at,
                  visible_at - :ttl AS db_now
    """), {"run_id": claimed.run_id, "worker": claimed.lease_owner,
           "epoch": claimed.lease_epoch, "ttl": ttl}).fetchone()
    if row is None:
        return None  # lease lost -- caller must not proceed to any write
    proof = LeaseProof(claimed.run_id, row.lease_owner, row.lease_epoch, conn, conn.get_transaction())
    return FencedGuardResult(proof, row.cancel_requested_at, row.deadline_at, row.db_now)


def append_event(conn: Connection, proof: LeaseProof, level: str,
                  node_key: Optional[str], message: str) -> None:
    _check_proof(conn, proof)
    conn.execute(text("""
        INSERT INTO run_events (run_id, seq, level, node_key, message, ts)
        SELECT :run_id, COALESCE(MAX(seq), 0) + 1, :level, :node_key, :message, now()
        FROM run_events WHERE run_id = :run_id
    """), {"run_id": proof.run_id, "level": level, "node_key": node_key, "message": message})
```

**Why `visible_at` does not appear in any of these `WHERE` clauses** (heartbeat,
T2, T3, park, T4): the hazard that would motivate it — a worker whose lease has
technically lapsed renewing it anyway and "resurrecting" ownership — is already
fully closed by PostgreSQL's row-level locking plus `lease_owner`/`lease_epoch`
fencing, with no role for `visible_at`. Whichever of (a) the current worker's
heartbeat, or (b) another worker's T1 reclaim, acquires the row lock first fully
determines the outcome: if (a) wins, it's the still-alive worker correctly
self-healing (exactly Risk R3's intended recovery path, via the dedicated
heartbeat thread); if (b) wins, the original worker's *next* fenced write finds
its epoch superseded and stops. Adding a `visible_at` check to these operations
would reintroduce spurious lease loss for a merely-slow (not dead) worker — the
specific failure mode the heartbeat-thread design exists to prevent. `T1` remains
the **sole** operation that intentionally gates on `visible_at <= now()`.

### 4.2 T1 — Claim/reclaim

Given in full in section 3.1 (`claim_run()`). The underlying SQL, for reference:

```sql
BEGIN;
SELECT id, status AS prev_status FROM runs
 WHERE status IN ('queued','waiting','running') AND visible_at <= now()
 ORDER BY visible_at LIMIT 1
 FOR UPDATE SKIP LOCKED;
-- prev_status, captured here before the UPDATE applies, is what decides
-- whether this claim is an ordinary claim or a genuine reclaim -- see
-- claim_run() in section 3.1 for the exact condition and why
-- `recovery_count > 0` alone is the wrong (and previously incorrect) test.

UPDATE runs SET
   status = 'running', lease_owner = :worker,
   lease_epoch = lease_epoch + 1,
   recovery_count = recovery_count + CASE WHEN status = 'running' THEN 1 ELSE 0 END,
   visible_at  = now() + :ttl,
   started_at  = COALESCE(started_at, now()),
   deadline_at = COALESCE(deadline_at, now() + :run_timeout)
 WHERE id = :id
RETURNING lease_epoch, recovery_count, cancel_requested_at, deadline_at, queue_deadline_at;
COMMIT;
```

**Post-claim checks, in order** (`docs/architecture.md` §4.3; `db_now` is the first
fenced guard's reading, check 1 uses `ClaimedRun.prev_status`): queue
timeout → finalize `timed_out`; run deadline passed → resolve orphans (Run-deadline
column, §4.8 item 3) and leftover `retry_wait` rows (§4.10), then finalize
`timed_out` via T4, whose in-statement deadline term (§4.5) agrees;
`recovery_count > max_recoveries` → resolution-only pass, finalize
`failed`/`max_recoveries_exceeded`; `cancel_requested_at` set → resolution-only
pass per §6.2; otherwise run the scheduler loop. Orphan resolution runs after
**every** claim — including `prev_status = 'waiting'`, which is how SIGTERM
leftovers are recovered (§4.11) — keyed on `started_epoch < lease_epoch`, not on
how the run reached the claim.

### 4.3 T2 — Node start (corrected: state-transition-safe, due-retry-enforced, explicit cancellation/deadline exit)

The fenced guard that opens T2 returns `cancel_requested_at` and `deadline_at`
(section 3's `FencedGuardResult`) — the original draft obtained these values but
then proceeded directly to the `node_runs` write regardless of what they said.
Corrected: both are checked **before** any `node_runs` write is attempted, in the
same transaction the fenced guard already opened:

```python
class StartNodeResult(Enum):
    STARTED = auto()
    LEASE_LOST = auto()
    CANCELLED = auto()
    DEADLINE_EXCEEDED = auto()
    ENGINE_INCONSISTENCY = auto()

def start_node(conn, claimed: ClaimedRun, node_key: str,
               resolved_class: EffectClass, ttl: int) -> StartNodeResult:
    with conn.begin():
        guard = run_fenced_guard(conn, claimed, ttl)
        if guard is None:
            return StartNodeResult.LEASE_LOST   # nothing further written; caller stops

        # ORDER MATTERS: deadline is checked BEFORE cancellation. If both
        # are true at once (a cancel was requested and the run deadline
        # has also already passed), the run must resolve as timed_out,
        # not cancelled -- see "Precedence" below.
        if guard.deadline_at <= guard.db_now:
            # Do NOT start a new node. The fenced guard's own renewal
            # (visible_at) is still committed below -- the worker
            # genuinely still holds the lease and should keep it while
            # it performs resolution -- but no node_runs write happens
            # in this transaction. The caller exits T2 and the
            # execution loop enters the drain of section 4.8 item 3 /
            # section 4.9: no new starts, live attempts finish and
            # persist normally (they are NOT interrupted by the
            # deadline), and the run is finalized timed_out only once
            # every live attempt is resolved (architecture.md section
            # 4.6; the same finalization post-claim check 2 performs
            # for a claimer, applied here mid-run).
            # guard.db_now, never the worker's own clock, is what this
            # comparison uses (architecture.md section 4).
            return StartNodeResult.DEADLINE_EXCEEDED

        if guard.cancel_requested_at is not None:
            # Same shape, for cancellation: do not start a new node; the
            # renewal still commits; the caller must not proceed with
            # :node_key at all. It exits T2 and lets the execution
            # loop's overall orchestration enter cancellation
            # resolution: already in-flight nodes elsewhere in this run
            # are left to finish naturally (U5 drain, architecture.md
            # section 6.2a) -- this function has no bearing on them,
            # since it only ever concerned whether THIS prospective
            # node-start should happen -- and once every in-flight node
            # has drained, the run is resolved per the interruption
            # matrix (section 6.2) and finalized (T4). This is the same
            # cancellation-observation flow as section 4.7, just
            # reached from a would-be node-start rather than a
            # heartbeat tick.
            return StartNodeResult.CANCELLED

        row = conn.execute(text("""
            INSERT INTO node_runs (run_id, node_key, status, attempt, failures,
                                   outcome, started_epoch, effect_class, started_at)
            VALUES (:run_id, :node_key, 'running', 1, 0, 'known', :epoch,
                    :resolved_class, now())
            ON CONFLICT (run_id, node_key) DO UPDATE SET
                   status        = 'running',
                   attempt        = node_runs.attempt + 1,
                   started_epoch  = :epoch,
                   started_at     = now(),
                   retry_at       = NULL
                   -- failures deliberately absent: preserved, per
                   -- architecture.md section 5.1 ("attempt counts
                   -- every start; failures counts only ordinary
                   -- failures").
             WHERE (node_runs.status = 'retry_wait' AND node_runs.retry_at <= now())
                OR (node_runs.status = 'running'    AND node_runs.started_epoch < :epoch)
            RETURNING run_id, node_key, status, attempt, effect_class
        """), {"run_id": claimed.run_id, "node_key": node_key,
               "epoch": claimed.lease_epoch, "resolved_class": resolved_class}).fetchone()
        # Legal prior states: absent (plain INSERT path), retry_wait with
        # retry_at already due, or running at an OLDER epoch (a genuine
        # orphan). A conflicting row that is terminal, a not-yet-due
        # retry_wait, or a genuinely live running row (same/newer epoch)
        # matches neither branch ⇒ 0 rows from RETURNING ⇒ left
        # untouched ⇒ engine_inconsistency (same category as the
        # existing deadlock assertion, architecture.md section 4.5).
        if row is None:
            return StartNodeResult.ENGINE_INCONSISTENCY

        append_event(conn, guard.proof, "info", node_key, "node started")

    return StartNodeResult.STARTED
```

The due-retry check (`retry_at <= now()`) is enforced in two places by design: the
pure scheduler (`evaluate_readiness()`/`plan_next_step()`, unchanged M1 code) is
the first line, deciding whether a node is even proposed as ready; this `WHERE`
clause is the persistence-layer backstop, so a bug upstream cannot start a retry
early. The `retry_wait_requires_retry_at` CHECK constraint (section 2) guarantees
`retry_at` is never `NULL` when this comparison runs.

**Precedence when both conditions hold:** if `guard.deadline_at <= guard.db_now`
**and** `guard.cancel_requested_at is not None` in the same guard result,
`start_node()` returns `DEADLINE_EXCEEDED`, never `CANCELLED`. This preserves the
accepted architecture's timeout precedence at the T2 decision point: the run
deadline is a natural terminal cause (`docs/architecture.md` §4.3 post-claim
check 2 and §4.6 — "`timed_out`, with interrupted nodes resolved per §6.2"), and
§6.2a/ADR-0009 give natural `failed`/`timed_out` precedence over `cancelled` in
T4's `CASE` ("real failures are never masked"; precedence `failed`/`timed_out` >
`cancelled` > `succeeded`). Checking cancellation first would classify the run's
resolution path as cancellation even though T4 would ultimately finalize
`timed_out` anyway — the T2 ordering must not contradict the T4 ordering it
feeds into. The cancel request is not lost: `cancel_requested_at` stays set on
the row, and the deadline-resolution path's interruption handling already
accounts for it per §6.2 (an `outcome_unknown` from deadline ends the run
`timed_out` with `has_unknown_outcome = true`, never relabeled `cancelled`).

**On `CANCELLED`/`DEADLINE_EXCEEDED`:** these are per-node-start outcomes, not a
run-level decision made by this function. Either one means: stop proposing new
node-starts for this run, then resolve and finalize. They differ in what happens
to nodes already in flight: for `CANCELLED`, section 4.7's cancellation-observation
flow applies and in-flight nodes **drain naturally (U5)**, per architecture
§6.2a/ADR-0009; for `DEADLINE_EXCEEDED`, section 4.8 item 3 / §4.9 applies (Option
B, approved — §11 D-A) and in-flight nodes likewise **drain** and are not
interrupted by the deadline. The two remain distinct causes: the run ends
`cancelled` versus `timed_out`, and deadline takes precedence if both hold.
Nothing about *other*, already-running nodes is changed by this function merely
returning either value for one prospective start, and the reordering of the two
checks does not alter either path.

### 4.4 T3 — Node finish

Same shape as T2 — fenced guard first, then the node write, any newly-`skipped`
downstream rows, and the `run_events` append, all in one transaction under the
lock the fenced guard's `UPDATE` took — but, unlike the original sketch, the node
write carries an **explicit atomic authorization predicate**, so a late or stale
result can never overwrite a node that has since been resolved:

```python
class FinishNodeResult(Enum):
    PERSISTED = auto()
    LEASE_LOST = auto()
    RESULT_DISCARDED = auto()        # guarded UPDATE matched 0 rows (see below)
    ENGINE_INCONSISTENCY = auto()

def finish_node(conn, claimed: ClaimedRun, node_key: str, attempt: int,
                finish: NodeFinish, ttl: int) -> FinishNodeResult:
    # `attempt` is the value T2's RETURNING gave this attempt (section 4.3);
    # `finish` carries the status/outcome/output/error/failure_inc/delay
    # decided by the pure M1 engine.
    with conn.begin():
        guard = run_fenced_guard(conn, claimed, ttl)
        if guard is None:
            return FinishNodeResult.LEASE_LOST   # write nothing further

        row = conn.execute(text("""
            UPDATE node_runs SET
                   status   = :status,
                   outcome  = :outcome,
                   output   = :output,
                   error    = :error,
                   failures = failures + :failure_inc,
                   retry_at = CASE WHEN CAST(:status AS text) = 'retry_wait'
                                   THEN now() + CAST(:delay AS double precision)
                                               * interval '1 second'
                                   ELSE NULL END
             WHERE run_id = :run_id AND node_key = :node_key
               AND status = 'running'          -- not already resolved/terminal/retry_wait
               AND started_epoch = :epoch      -- started under THIS lease epoch
               AND attempt = :attempt          -- this attempt, not a later one
            RETURNING status, attempt
        """), {...}).fetchone()

        if row is None:
            # Authorized (lease verified above) but the node is no longer in
            # the state this result was produced for. Discard the result.
            seen = conn.execute(text("""
                SELECT status, attempt, started_epoch FROM node_runs
                 WHERE run_id = :run_id AND node_key = :node_key
            """), {...}).fetchone()
            if seen is None:
                return FinishNodeResult.ENGINE_INCONSISTENCY   # T2 always wrote a row
            append_event(conn, guard.proof, "warning", node_key,
                         f"late result discarded: node is {seen.status} "
                         f"(attempt {seen.attempt}), result was for attempt {attempt}")
            return FinishNodeResult.RESULT_DISCARDED  # commits ONLY the warning event

        # Only reached when exactly one node row was authorized to change:
        # write skipped rows for newly unreachable downstream nodes
        # (INSERT ... ON CONFLICT DO NOTHING) and the node-finished event.
        ...
    return FinishNodeResult.PERSISTED
```

**Atomic authorization conditions** (all must hold in the one transaction, and
each is enforced by SQL, not by in-memory state):

| Condition | Enforced by |
|---|---|
| Run still active (`status = 'running'`) | fenced guard's `WHERE status = 'running'` |
| Current lease owner **and** epoch match | fenced guard's `WHERE lease_owner = … AND lease_epoch = …` |
| Node row is still `running` | `node_runs … WHERE status = 'running'` |
| Node was started under the current epoch | `… AND started_epoch = :epoch` |
| This result belongs to this attempt | `… AND attempt = :attempt` |
| Not overwriting a resolved node | any of `succeeded`/`failed`/`skipped`/`cancelled`/`retry_wait` fails `status = 'running'` ⇒ 0 rows |

`attempt = :attempt` goes beyond the minimum list and is needed: within one
epoch, an attempt that was interrupted (e.g. node timeout ⇒ `retry_wait`) can be
followed by a later attempt (`retry_wait → running`, attempt N+1) while the
earlier attempt's task is still alive. Its late result would otherwise satisfy
`status = 'running' AND started_epoch = :epoch` and overwrite attempt N+1.

**What the predicate deliberately does *not* contain:**
- **No `visible_at` condition.** A legitimate result must not be rejected
  because `visible_at` has elapsed with no other worker having reclaimed
  (section 3.1: epoch+owner fencing, not `visible_at`, is the authorization). The
  fenced guard's own `UPDATE` renews `visible_at` as a side effect, so a merely
  slow worker self-heals; if another worker *did* reclaim, the guard matches 0
  rows ⇒ `LEASE_LOST`.
- **No rejection on `cancel_requested_at` or an expired `deadline_at`.** A
  result already in hand is persisted while the node is still `running`: the
  node genuinely completed (its side effects happened, its outcome is known),
  and architecture §6.2a already states that finalization never rewrites node
  rows and that a cancelled run may coexist with completed nodes' real outputs.
  By §6.2's definition an *interruption* is an attempt "without a recorded
  result", so a result recorded before an interruption is applied means that
  attempt was not interrupted. The `status = 'running'` predicate is the sole
  arbiter between a result and an interruption resolution for the same attempt.

**Zero-row behavior.** If the fenced guard succeeds but the node `UPDATE` matches
0 rows, the worker **discards the result**: it writes no node state, no skip rows,
and no downstream effect; it records one `warning` event through the proof (so the
transaction commits only that event) and returns `RESULT_DISCARDED`. This is a
normal, benign outcome when a node was already resolved by interruption,
cancellation resolution, timeout resolution, or a later attempt. A missing node
row is different — T2 always creates the row — and is `ENGINE_INCONSISTENCY`. If
the *guard* matched 0 rows, the result is simply abandoned as `LEASE_LOST`.

**Interruption-resolution writes use the same predicate.** Every non-orphan
resolution of a live attempt (cancel, node timeout, run deadline) is a T3-shaped
write with the identical `status = 'running' AND started_epoch = :epoch AND
attempt = :attempt` predicate; a reclaimer's *orphan* resolution uses
`status = 'running' AND started_epoch < :epoch` (the T2 orphan condition,
section 4.3). Whichever of {result, resolution} commits first wins; the other
matches 0 rows. Both begin with the fenced guard, so they serialize on the
`runs` row lock.

`retry_at` is always computed as `now() + :delay * interval '1 second'` in this
SQL, where `:delay` comes from `flowforge.engine.retry.compute_backoff()` (pure,
unchanged) — never from `flowforge.engine.interruption.py`'s own `retry_at`
field, which is computed against the pure-engine `Clock` port for unit-test
purposes only and is not database-authoritative.

### 4.5 Heartbeat, park, T4 finalize

The heartbeat is `run_fenced_guard()` (section 3.1). Ordinary park is unchanged
from `docs/architecture.md` §4.5; T4 is architecture §6.2a **plus** two additions
specified here (atomic deadline precedence — D-D — and a no-unresolved-node
guard).

```sql
-- Park (ordinary; architecture section 4.5, unchanged)
UPDATE runs SET
   status = 'waiting', lease_owner = NULL,
   visible_at = LEAST(
       (SELECT min(retry_at) FROM node_runs WHERE run_id = :id AND status = 'retry_wait'),
       deadline_at)
 WHERE id = :id AND status = 'running'
   AND lease_owner = :worker AND lease_epoch = :epoch
   AND cancel_requested_at IS NULL
RETURNING status;
```

The architecture's "park only with no in-flight node tasks" is a **worker-side
precondition in the prose, not a condition in this SQL** (the statement never
looks at `node_runs`). That is why a fenced park can also serve the
graceful-release case of §4.11, which deliberately parks while attempts are still
running — through a **dedicated** statement, `park_for_shutdown()` (D-H), that
leaves this ordinary park, including its `cancel_requested_at IS NULL` predicate,
unchanged.

```sql
-- T4 finalize: ONE atomic statement, fenced, one clock sample (D-D). Issued only
-- through run_t4(), i.e. only inside a transaction whose fenced guard succeeded.
WITH s AS MATERIALIZED (SELECT clock_timestamp() AS t)     -- the ONE authoritative sample
UPDATE runs r SET
   status = CASE
      WHEN r.deadline_at <= s.t                              THEN 'timed_out'      -- (1) deadline: decided HERE, on s.t, against the locked row
      WHEN CAST(:natural AS text) IN ('failed', 'timed_out') THEN CAST(:natural AS text) -- (2) a real failure is never masked by a cancel
      WHEN r.cancel_requested_at IS NOT NULL                 THEN 'cancelled'      -- (3) a cancel that committed first wins
      ELSE CAST(:natural AS text) END,                                              -- (4) 'succeeded' | 'cancelled'
   finished_at = s.t,                                        -- the SAME sample the deadline comparison used
   error = :err, lease_owner = NULL,
   has_unknown_outcome = EXISTS (
       SELECT 1 FROM node_runs WHERE run_id = :id AND outcome = 'unknown')
  FROM s
 WHERE r.id = :id AND r.status = 'running'
   AND r.lease_owner = :worker AND r.lease_epoch = :epoch
   AND NOT EXISTS (                                          -- no live attempt, no unresolved retry
       SELECT 1 FROM node_runs
        WHERE run_id = :id AND status IN ('running', 'retry_wait'))
RETURNING r.status, r.finished_at;
```

```python
def run_t4(conn, proof: LeaseProof, claimed: ClaimedRun, natural: str, err):
    _check_proof(conn, proof)     # refuse before any SQL unless THIS transaction's guard succeeded
    return conn.execute(text(T4_SQL), {...}).fetchone()
```

**D-D precedence (approved).** If T4 finalizes the run before the deadline is
confirmed, the normal result stands. If the deadline is confirmed before T4
finalizes, the final status is `timed_out` even if some nodes failed. Node rows,
their failures, and every `outcome_unknown` are never rewritten to match the
run-level status (architecture §6.2a: "Node rows are never rewritten by
finalization"), and `has_unknown_outcome` is still derived from the node rows.

- **Term (1) is the deadline decision, made atomically.** `deadline_at` is read
  from the row being finalized and compared with the database sample `s.t`; no
  earlier Python-side clock check is relied on. This extends ADR-0009's rule that
  the terminal status is "computed from the row as locked at statement time" and
  keeps its precedence `failed`/`timed_out` (natural) > `cancelled` > `succeeded`;
  it adds only that a database-confirmed deadline outranks a natural `failed`.
- **One authoritative clock sample.** PostgreSQL documents that `clock_timestamp()`
  "changes even within a single SQL statement", so the previous form — separate
  calls for the status `CASE` and for `finished_at` — could straddle the deadline
  and commit a normal status with `finished_at >= deadline_at`, or `timed_out` with
  `finished_at < deadline_at`. `s` is a **materialized** CTE (PostgreSQL's
  documentation: folding "can be prevented by marking the WITH query as
  MATERIALIZED"; a volatile query is never folded), evaluated once, and both the
  deadline comparison and `finished_at` read `s.t`. Hence for every outcome
  `(status = 'timed_out') ⇔ (finished_at >= deadline_at)` whenever `:natural` is
  not itself `'timed_out'`.
- **The sample is taken after the lock — by statement order, not CTE order.** T4 is
  executed only through `run_t4()`, which refuses without a valid `LeaseProof`
  from the **same transaction**. That proof exists only after `run_fenced_guard()`
  succeeded, and the guard's `UPDATE` took the `runs` row lock, which PostgreSQL
  holds until transaction end. So every part of this statement, including the one
  clock sample, executes while the lock is already held; the statement's own
  `WHERE` still carries the full fence (`status`, owner, epoch) as defense in depth.
- **What is deliberately not relied on.** PostgreSQL's documentation says "the
  primary query and the WITH queries are all (notionally) executed at the same
  time" and gives no ordering between a CTE and a row lock, and it does not say when
  target-list or `SET` expressions are evaluated relative to a lock. A self-locking
  statement — `WITH locked AS (SELECT … FOR UPDATE), s AS (SELECT clock_timestamp()
  FROM locked) UPDATE …` — was considered and **not adopted as the guarantee**: it
  would rest on undocumented executor data flow rather than on a documented
  property (locks held to transaction end). This document therefore also does not
  claim that `SET` expressions are re-evaluated after a lock wait (see §11,
  corrections to earlier statements).
- **The worker's `:natural` is no longer the sole basis.** When the loop's
  `deadline_confirmed` flag is set it passes `:natural = 'timed_out'`; term (1)
  is the atomic backstop for a deadline the loop has not yet confirmed. They agree
  because `deadline_at` never moves; if the database clock were stepped backwards
  after confirmation (Risk R8), term (2) still yields `timed_out` from `:natural`.
- **Consequence, flagged in §11:** a run whose nodes all succeeded but whose T4
  executes at or after `deadline_at` finalizes `timed_out` (node rows stay
  `succeeded`). That follows directly from deciding the deadline atomically in T4.
- **The `NOT EXISTS` predicate** makes two invariants database-enforced: T4 cannot
  commit while any node row is `running` (a live attempt, or an unresolved
  orphan) or `retry_wait`, so **no terminal run can hold an unresolved
  `retry_wait` row** (§4.10) and T4 is never issued over a live attempt (§4.9).
  Nodes never started are absent rows and do not block it. It is evaluated in the
  statement's snapshot: it relies on the single-writer-per-lease rule and on the
  loop issuing T4 only after it has awaited every T3/resolution transaction, not
  on a lock on `node_runs`.
- **Zero rows.** `finalize_run()` (§4.10) rolls back and returns `NOT_FINALIZED`;
  the worker then runs `run_fenced_guard()` in a new transaction: `None` ⇒ the
  lease is lost, stop writing. Otherwise a node row is still `running` or
  `retry_wait` although no current-epoch attempt is live. On the deadline path an
  older-epoch orphan or a pending retry is resolved inside `finalize_run()` itself
  (D-I), so what remains is an inconsistency (an orphan on a non-deadline path, or
  a stray row under `natural = 'succeeded'`): log `engine_inconsistency`, stop the
  loop, and leave the run for lease expiry — the next claimer sees any such row as
  an orphan and resolves it by §6.2 (post-claim check 2 if the deadline has
  expired, otherwise the Crash column).

Race cases for this statement are rows 23–26 and 40–41 of §8; the orphan/retry resolution
that precedes it is §4.10, rows 33–38.

### 4.6 API cancel

```sql
UPDATE runs SET
   cancel_requested_at = COALESCE(cancel_requested_at, now()),
   status      = CASE WHEN status = 'queued' THEN 'cancelled' ELSE status END,
   finished_at = CASE WHEN status = 'queued' THEN now() ELSE finished_at END,
   visible_at  = CASE WHEN status = 'waiting' THEN now() ELSE visible_at END
 WHERE id = :id AND status IN ('queued', 'waiting', 'running')
RETURNING status;    -- 0 rows ⇒ already terminal ⇒ HTTP 409
```

**The API never writes `run_events`, under any branch** — confirmed directly
against `docs/architecture.md` §17's writers table ("`node_runs`/`run_events`: the
fenced lease holder only... the worker writes everything else"). This matters
per-case:

- **`queued → cancelled`:** no `node_runs` rows ever existed, no lease was ever
  held — there is no fenced lease holder whose narrative a `run_events` row would
  belong to. **No event is required or written.** The run's own `status`/
  `finished_at` columns are the complete record.
- **`waiting`:** the flag and `visible_at` are set; the run is *not* finalized by
  the API. The next worker to claim it (`claim_run()`, `prev_status='waiting'`)
  becomes the new fenced holder, observes `cancel_requested_at` as post-claim
  check 4, and records whatever events its own resolution pass needs, under its
  own, freshly-obtained `LeaseProof`.
- **`running`:** only the flag is set. The *current* holder observes it via the
  same `FencedGuardResult.cancel_requested_at` its own next heartbeat tick
  already returns — never a separate, unfenced read.

### 4.7 Cancellation observation flow (running case), explicit sequence

1. Heartbeat thread, its own connection/transaction: calls `run_fenced_guard()`.
   If successful, `FencedGuardResult.cancel_requested_at` carries the flag.
2. That transaction commits (releasing the row lock). The heartbeat's
   `LeaseProof` is now unusable (and was never meant to survive past here). The
   heartbeat thread sets a plain `threading.Event` if the flag was set — nothing
   database-shaped crosses the thread boundary.
3. The execution loop (a different task) observes that signal.
4. The execution loop opens its **own new transaction**, on its own connection,
   and calls `run_fenced_guard()` again — using the same cached
   `ClaimedRun.lease_epoch`, never anything from the heartbeat's now-dead proof —
   producing a fresh `LeaseProof` scoped to this transaction.
5. Only if that succeeds may it call `append_event()` and perform the
   interruption-resolution writes §6.2 requires, in this same transaction. The
   fresh guard's result also carries `deadline_at` and `db_now`: if the run
   deadline has expired at this point, the loop additionally sets
   `deadline_confirmed` (§4.9). Live nodes keep draining exactly as in the cancel
   case (the deadline interrupts nothing), and the run's natural outcome is
   `timed_out`, not `cancelled` — the same deadline-over-cancellation precedence
   section 4.3 applies at T2 and that T4's `CASE` applies at finalization — even
   though `cancel_requested_at` is also set.
6. If it fails (0 rows — the lease moved between steps 2 and 4), the execution
   loop stops writing anything further for this run immediately, exactly like
   any other lease-loss detection.

### 4.8 Run-deadline observation by the live worker

`docs/architecture.md` §4.6 assigns run-timeout enforcement to "the live worker's
timer; any later claimer (check 2); a parked run wakes at `deadline_at`". T2
(§4.3), the fresh guard in §4.7, and post-claim check 2 each detect expiry only
when something else happens to run a fenced guard. A live worker whose run is
momentarily idle (all in-flight nodes mid-execution, no heartbeat tick due, no
node ready) must still notice the deadline passing. Contract:

1. **A local wait mechanism signals the execution loop.** The execution loop
   (the asyncio side — not the heartbeat thread) includes a timed wait on "the
   deadline is expected to be reached" alongside its existing waits (node
   completions, the cancellation signal, scheduling wake-ups). It is armed from
   the `db_now` of the most recent `FencedGuardResult` (the first fenced guard after
   the claim arms it) — as
   `remaining = deadline_at - db_now` (both values database-supplied), counted
   down on the worker's **monotonic** clock from the moment that reading was
   received, and **re-armed** each time a newer database reading arrives. The
   worker's wall clock is never compared against `deadline_at`. This is a timed
   wait inside the existing loop — **no new timer service, thread, or
   table**. `deadline_at` is set once at first claim (T1's `COALESCE`) and never
   moves, so re-arming only refreshes the *remaining* estimate.
2. **The signal is not authoritative.** When it fires, the loop does **not**
   act on it. It opens its own new transaction and runs a fresh
   `run_fenced_guard()` (same discipline as §4.7 steps 4–6) and decides using
   that result's `guard.deadline_at <= guard.db_now` — the database's reading at
   that statement. No `node_runs`, `run_events`, or `runs` write is made on the
   strength of the local signal alone. If the guard returns `None`, the lease
   is lost: stop writing, exactly as everywhere else.
3. **If the database confirms expiry** — **Option B (approved): stop scheduling
   and starting new nodes and drain live attempts.** The run deadline is an
   independent interruption cause for *nodes left started-without-result*
   (architecture §6.2 lists "run deadline" as its own cause, with its own matrix
   column), but it is **not** permission to overwrite a live result, bypass U5, or
   forcibly cancel an external operation. The live worker, still the fenced lease
   holder:
   - **Stops scheduling and starting new nodes immediately** — including due
     `retry_wait` retries and nodes that a result landing during the drain would
     otherwise make ready. The loop stops proposing starts, and T2 independently
     refuses (`DEADLINE_EXCEEDED`, §4.3), so a stale in-memory flag can never
     cause a start.
   - **Does not interrupt live attempts because of the deadline.** No
     deadline-driven cancellation event, `task.cancel()`, or abandonment. This
     matches ADR-0009's U5 rationale ("forcing a stop on an external write would
     itself manufacture a new outcome-unknown case") and §6.2's "drain, don't
     cancel mid-flight, to avoid manufacturing further ambiguity".
   - **Lets already-running attempts finish and persist their legitimate
     results** through `finish_node()` under the fenced guard and the §4.4
     predicate, exactly as before the deadline (natural failures and
     retry-eligible failures are written as usual; none is rejected because the
     deadline has passed).
   - **Applies the existing rules when an attempt cannot complete normally:**
     the per-node timeout (executor-enforced, §6.2 **Node timeout** column — e.g.
     `idempotent_write` ⇒ `retry_wait` unknown while budget remains, `unsafe_write`
     ⇒ `failed`/`outcome_unknown`), and lease loss/crash (the claimer path below).
     The run deadline neither alters nor substitutes for these.
   - **Finalizes `timed_out` via T4 only after every live attempt is resolved**
     (a persisted result, a node-timeout resolution, or the lease being lost).
     `:natural = 'timed_out'`, whose `CASE` gives it precedence over `cancelled`
     even if `cancel_requested_at` is also set (§6.2a/ADR-0009; consistent with
     §4.3's deadline-before-cancellation ordering). T4 additionally re-derives the
     deadline atomically from database time inside the statement (§4.5, D-D), so
     the worker's `:natural` is never the sole basis. Nodes that never started stay
     absent ("not reached", §3.1).
   - **Preserves unknown outcomes.** T4 computes `has_unknown_outcome` from the
     node rows. Nothing infers that an external side effect did not execute
     merely because the local worker stopped waiting for it (§4.9 item 5).

   **Where the Run-deadline column does apply.** To nodes left
   started-without-result that no live attempt of the current holder is draining —
   **orphans**, i.e. `running` rows whose `started_epoch` is older than the run's
   current `lease_epoch`. They are resolved in two places, by the same column:
   (a) a later claimer's post-claim check 2 ("resolve any orphans (§6.2), then
   finalize `timed_out`", architecture §4.3); and (b) **the current holder itself,
   immediately, when it confirms the deadline mid-run** — an orphan that has not
   yet been re-executed (for example it is waiting for a concurrency slot) can no
   longer be restarted because T2 refuses, so `finalize_run()` step 2 resolves it
   in the same fenced transaction, with no wait for another lease expiry (§4.10,
   D-I). Orphans are **never re-executed** after expiry (re-executing would start
   new work after the deadline, so the matrix's *Crash* column "Re-execute" does
   not apply). The cells, unmodified from §6.2:

   | Effect class of the node left started-without-result | Node row written (§6.2 Run deadline column) |
   |---|---|
   | `pure` | `cancelled`, known |
   | `read` | `cancelled`, known |
   | `idempotent_write` | `cancelled`, **unknown** |
   | `unsafe_write`, provably not dispatched (live worker only; a crash can never prove this, so an orphan is never in this row) | `cancelled`, known |
   | `unsafe_write`, dispatched or unprovable (every orphan) | `failed`, `outcome_unknown`, **unknown** |

   No cell retries, and an `idempotent_write` here does **not** take the
   `retry_wait` path — that is the **Node timeout** column's rule (implemented by
   `resolve_idempotent_write_timeout`) and is never used for the run deadline. An
   `unsafe_write` left `failed`/`outcome_unknown` does not make the run `failed`:
   per §6.2, "an `outcome_unknown` from cancel or deadline ends the run
   `cancelled` / `timed_out`, with `has_unknown_outcome = true`".

   **Crash or lease loss during the drain:** the draining worker stops writing
   (fenced guard returns 0 rows); after lease expiry a claimer runs post-claim
   check 2 and applies the table above to the orphans (and §4.10 to the pending
   retries), then finalizes `timed_out`; orphans of *earlier* epochs that exist
   while the current holder is still draining are resolved immediately by
   `finalize_run()` step 2 (D-I) rather than waiting for that. **Bound:** the drain adds at most the longest live attempt's
   remaining per-node timeout (default 5 min, architecture §4.6) after
   `deadline_at`; a consequence of Option B, accepted. **Leftover `retry_wait`
   rows** when the drain completes are *not* live attempts, are never resumed,
   and are resolved before T4 by the §4.10 rules (D-E).
4. **If the timer fires early** (clock drift between the monotonic clock and the
   database clock, event-loop scheduling latency, or any estimation error) the
   fresh guard returns `deadline_at > db_now`: the deadline has **not**
   expired, no deadline action is taken, and the loop re-arms from the guard's
   new `db_now` (with a small minimum delay so a persistently-early timer cannot
   busy-spin). The guard's `visible_at` renewal is a harmless side effect. The
   database check always decides — a firing timer is a hint to go ask, never a
   verdict. The converse failure (timer late or never delivered) is bounded by
   the backstops that already exist: every heartbeat tick, T2, and T3 runs a
   fenced guard that carries `deadline_at`/`db_now`, and a parked run is woken
   at `deadline_at` by its `LEAST(...)` `visible_at` (architecture §4.5).
5. **Run deadline is not a node timeout.** The node timeout (architecture §4.6:
   starts at that attempt's T2, ends at that attempt's end, enforced by the
   executor, resolved via the §6.2 **Node timeout** column, retries allowed per
   policy) is unchanged, independent, and not shortened, extended, or
   re-classified by this mechanism. Conversely, a node timeout never consumes or
   resets the run deadline (§4.6: nothing resets it). The two use different
   columns of the §6.2 matrix and different error causes (`deadline` vs
   `timeout`).
6. **Three causes, not to be merged.** The run deadline, the per-node timeout,
   and the crash/node-timeout `outcome_unknown` U5 rule are different mechanisms
   with different scopes and consequences, each taken from the existing
   architecture:

   | | Run deadline | Per-node timeout | Crash / lease loss, and node-timeout `outcome_unknown` (U5) |
   |---|---|---|---|
   | Scope | Whole run; DB-confirmed (§4.8) | One node attempt, from its T2; enforced by the executor | A node attempt orphaned by a lost lease (found at claim), or a timed-out `unsafe_write` / exhausted-budget `idempotent_write` with unknown outcome |
   | Live nodes | **Drained**: no new starts, live attempts finish normally; not interrupted by the deadline | Only the timed-out attempt is affected; siblings unaffected unless the timeout produces an unknown outcome (next column) | **Drained** — "drain, don't cancel mid-flight, to avoid manufacturing further ambiguity" (§6.2) |
   | Node resolution | Existing rules for any attempt that ends abnormally (node timeout, crash); the §6.2 **Run deadline** column for nodes left started-without-result (orphans at claim) | §6.2 **Node timeout** column (retry per policy; `idempotent_write` → `retry_wait` while budget remains) | §6.2 **Crash** / **Node timeout** columns |
   | Run-level result | `timed_out`; `has_unknown_outcome = true` if any unknown | Per the node's retry policy and `on_error`; a timed-out `unsafe_write` (or exhausted-budget `idempotent_write`) with unknown outcome is the U5 case in the next column | Run ends **`failed`, ignoring `on_error`** (§6.2) |
   | Error cause | `deadline` | `timeout` | `crash` / `lease_lost` / `timeout` |

   Architecture §6.2 states the run-level split: "An `outcome_unknown` from
   **crash or timeout fails the run** — it drains in-flight nodes (U5…)… and ends
   `failed`, ignoring `on_error`" versus "An `outcome_unknown` from **cancel or
   deadline** ends the run `cancelled` / `timed_out`, with `has_unknown_outcome =
   true`". Under Option B the deadline *also* drains live attempts (as does
   cancellation, §6.2a/ADR-0009), but it remains a distinct cause: it ends the run
   `timed_out`, uses the Run-deadline column, and is never merged with the
   node-timeout or crash rules. When the deadline and a U5 forced failure both
   apply to one run, D-D decides it: if the deadline is confirmed before T4
   finalizes, the run is `timed_out` and the node-level failure and unknown
   outcome are preserved (§4.5, §11 D-D).

### 4.9 Drain contract at confirmed run-deadline expiry

How the execution loop behaves once §4.8 item 2 has database-confirmed expiry.
This replaces the earlier live-interruption proposal; no interruption mechanism,
grace period, or abandoned-task bookkeeping exists for the deadline. **No new
parameters, no new service, no subprocess.**

1. **Entry.** The loop sets an in-memory `deadline_confirmed` flag only from a
   database-confirmed reading (a fresh fenced guard's `deadline_at <= db_now`,
   or the claimer's post-claim check 2). Caching it is safe because `deadline_at`
   never moves (T1's `COALESCE`); and a stale or wrongly-set flag cannot cause a
   start because T2 re-checks the database itself (§4.3).
2. **While draining, the loop does:** await live attempt tasks; persist their
   legitimate results via `finish_node()` (§4.4 predicate); apply per-node
   timeout resolution to an attempt that times out; keep heartbeating; handle a
   cancellation flag (a cancel requested during the drain changes nothing — the
   run still ends `timed_out`, §4.3 ordering and T4's `CASE`); and stop silently
   if the lease is lost.
3. **While draining, the loop does not:** call `start_node()` for any node
   (including a due `retry_wait` retry or a node newly made ready); set any
   node's cancellation event or call `task.cancel()` on any attempt *because of
   the deadline*; abandon an attempt; or overwrite a node row that has a live
   attempt. (The cancellation event stays reserved for cancellation, §4.7.)
4. **Completion.** On confirmation the loop calls `finalize_run(natural =
   'timed_out')` at once (§4.10): orphans of earlier epochs (D-I) and pending
   retries are resolved immediately, and the call returns `DRAINING` while any
   current-epoch attempt is live; the loop calls it again as each drain step
   completes (a draining attempt may itself leave a new `retry_wait` row) until
   it returns `FINALIZED`. T4 is **never** issued while a live attempt exists,
   and the database enforces it twice: `finalize_run()` step 4 counts
   current-epoch `running` rows, and T4's `NOT EXISTS` predicate refuses while
   any node row is `running` or `retry_wait`.
5. **External side effects.** The worker never cancels an external operation for
   the deadline, and never infers non-execution from having stopped waiting. If
   an attempt does end abnormally it is resolved by the existing matrix columns
   using the persisted `effect_class` (§5.2): a node timeout of an `unsafe_write`
   is `unknown` unless non-dispatch is proven (M3's dispatch marker; M2 fixtures
   supply it), an `idempotent_write` timeout is `retry_wait`/`unknown`, and an
   orphan found by a claimer is resolved by the Run-deadline column above. An
   outcome recorded `unknown` is never rewritten to `known` by the deadline path.
6. **Bound and limits.** Each live attempt is bounded by the executor-enforced
   per-node timeout (default 5 min), so the drain overruns `deadline_at` by at
   most the longest such remaining timeout. Python cannot preempt a coroutine or
   thread (a node that blocks the event loop delays node-timeout enforcement, the
   §4.8 timer, and this drain until it yields; state stays safe through fenced
   writes and the heartbeat thread, §4.7/architecture §4.4). How the executor
   stops waiting on a *timed-out* non-cooperating attempt is an executor-level
   M2.5 detail of the existing per-node-timeout mechanism, **unchanged and not
   decided by the run-deadline decision**; the late-result protections (§4.4
   predicate; fenced guard after finalization) are the same ones that already
   cover that case.
7. **Not SIGTERM.** Graceful shutdown (architecture §4.5) also stops claiming and
   lets in-flight nodes finish, but its post-state differs (the run continues
   on another worker, not `timed_out`). The two are not equated here: SIGTERM
   follows crash-recovery semantics (§4.11, D-C).

### 4.10 Finalization: resolving orphans and pending retries before T4 (D-E, D-F, D-G, D-I)

After the deadline is confirmed **no retry may start and no orphan may be
re-executed**: the loop stops proposing starts and T2 refuses (§4.3), including for
a due `retry_wait` row and for an orphan awaiting its re-execution. A `retry_wait`
row is a node waiting to be retried, and an orphan is a `running` row left by an
earlier lease epoch; neither is a live attempt of the current holder, nothing will
ever resume them once the run is finishing, and a non-terminal node row must not
survive into a terminal run (T4's predicate refuses it, §4.5). So **every
finalization path** — deadline, cancellation, and failure alike — goes through one
routine that resolves them and finalizes in a single fenced transaction:

```python
class FinalizeResult(Enum):
    FINALIZED = auto()
    DRAINING = auto()           # current-epoch live attempt(s) remain: T4 NOT executed
    LEASE_LOST = auto()
    NOT_FINALIZED = auto()      # T4 refused with no live attempt: unresolved rows (inconsistency)

def finalize_run(conn, claimed: ClaimedRun, natural: str, err, reason: str,
                 ttl: int) -> FinalizeResult:
    # `natural` is 'succeeded' | 'failed' | 'timed_out' | 'cancelled' (§4.5);
    # `reason` is free text for the events: "run deadline confirmed",
    # "run cancelled", or "run failing".
    with conn.begin() as txn:
        # 1. Acquire and validate the current fenced run guard.
        guard = run_fenced_guard(conn, claimed, ttl)
        if guard is None:
            return FinalizeResult.LEASE_LOST        # write nothing further

        if natural != 'succeeded':
            # 2. Resolve running ORPHANS (started_epoch < current lease_epoch)
            #    by the Run-deadline matrix. The statement itself checks that
            #    the deadline is database-confirmed; it is a no-op otherwise.
            for o in conn.execute(text(RESOLVE_DEADLINE_ORPHANS_SQL),
                                  {"run_id": claimed.run_id, "worker": claimed.lease_owner,
                                   "epoch": claimed.lease_epoch}).fetchall():
                append_event(conn, guard.proof, "warning", o.node_key,
                             f"orphan resolved at run deadline: {o.status}, outcome "
                             f"{o.outcome}; not re-executed")
            # 3. Resolve every pending retry_wait row, outcome preserved.
            for r in conn.execute(text(RESOLVE_PENDING_RETRIES_SQL),
                                  {"run_id": claimed.run_id}).fetchall():
                append_event(conn, guard.proof, "warning", r.node_key,
                             f"retry suppressed ({reason}); node resolved {r.status}, "
                             f"outcome {r.outcome} preserved")

        # 4. Any running node row of the CURRENT lease epoch is a live attempt.
        live = conn.execute(text(
            "SELECT count(*) FROM node_runs WHERE run_id = :run_id "
            "AND status = 'running' AND started_epoch = :epoch"),
            {"run_id": claimed.run_id, "epoch": claimed.lease_epoch}).scalar_one()
        if live > 0:
            # 5. Do NOT run T4. Steps 2-3 commit on their own (see below); the
            #    worker keeps draining and calls finalize_run again later.
            return FinalizeResult.DRAINING

        # 6. Nothing live and nothing pending: T4, with its atomic deadline term (§4.5).
        row = run_t4(conn, guard.proof, claimed, natural, err)     # §4.5; needs this transaction's proof
        if row is None:
            txn.rollback()          # all-or-nothing: steps 2-3 are undone too
            return FinalizeResult.NOT_FINALIZED
    # 7. Leaving the `with` block commits everything together.
    return FinalizeResult.FINALIZED
```

**Exact ordering, as specified (D-I):** (1) fenced guard; (2) orphans; (3)
`retry_wait` rows; (4) count current-epoch `running` rows; (5) if any, no T4 and
return `DRAINING`; (6) otherwise T4; (7) commit together. Rows with `started_epoch`
**equal to** the current epoch are live attempts of this worker and are never
resolved or interrupted by this routine — they drain normally (§4.9). The step-2
statement:

```sql
-- RESOLVE_DEADLINE_ORPHANS_SQL (finalize_run step 2): the existing §6.2 Run-deadline column
UPDATE node_runs n SET
       status   = CASE WHEN n.effect_class = 'unsafe_write' THEN 'failed' ELSE 'cancelled' END,
       outcome  = CASE WHEN n.effect_class IN ('idempotent_write', 'unsafe_write')
                       THEN 'unknown' ELSE n.outcome END,
       error    = CASE WHEN n.effect_class = 'unsafe_write'
                       THEN jsonb_build_object('code', 'outcome_unknown', 'cause', 'deadline',
                                               'message', 'orphaned attempt; dispatch cannot be disproven')
                       ELSE n.error END,
       retry_at = NULL
  FROM runs r
 WHERE n.run_id = :run_id
   AND r.id = n.run_id
   AND r.status = 'running'
   AND r.lease_owner = :worker AND r.lease_epoch = :epoch   -- fenced again, inside the statement
   AND r.deadline_at <= clock_timestamp()                   -- DB-confirmed expiry; never a Python flag
   AND n.status = 'running'                                 -- never a node a T3 already resolved
   AND n.started_epoch < r.lease_epoch                      -- strictly OLDER epoch: an orphan
RETURNING n.node_key, n.status, n.outcome, n.effect_class, n.attempt;
```

**Why this is safe, point by point.**

- **The existing matrix, applied exactly.** `pure`/`read` ⇒ `cancelled`, known;
  `idempotent_write` ⇒ `cancelled`, **unknown**; `unsafe_write` ⇒ `failed`,
  `outcome_unknown`, **unknown** — the "dispatched or unprovable" cell, because an
  orphan can never be shown not to have dispatched ("a crash can never prove
  this", §6.2). A fenced-out old worker is **not** evidence that its external
  operation did not execute; fencing stops its *database* writes, nothing more.
- **Uncertainty is only ever added, never removed.** `outcome` is set to `unknown`
  for the two write classes and otherwise left as recorded; the statement can never
  write `known`, so it cannot violate INV-U (§ below). `error.cause` is
  `deadline`, matching the column used.
- **Cannot bypass fencing.** The statement re-checks `lease_owner`/`lease_epoch`
  against the `runs` row itself in addition to the guard that opened the
  transaction. A worker that has been superseded matches 0 rows.
- **Cannot resolve the current epoch's rows or a newer epoch's.** `started_epoch <
  lease_epoch` excludes live attempts of this worker (equal), and a newer epoch
  would require this worker to have been superseded, which fails the fence.
- **Cannot overwrite a committed T3 result.** `n.status = 'running'` skips any row
  a T3 already moved to a terminal/`retry_wait` state. And no *legitimate* T3 can
  race it: a T3 by the **current** worker requires `started_epoch = :epoch`
  (§4.4), which an orphan never satisfies; a T3 by the **old** worker either
  committed before the new claim (then the row is not `running` and is skipped) or
  starts after it and fails its fenced guard on the epoch. An in-progress old T3
  holds the `runs` lock from its guard, and T1's `SKIP LOCKED` cannot claim the
  run until it commits.
- **No re-execution after confirmation, and no race with T2.** The deadline
  confirmed here is the same condition T2 refuses on. T2 and this statement
  serialize on the `runs` row lock: if a T2 committed first and legitimately
  restarted the orphan, that row now has `started_epoch = :epoch` — a live attempt,
  not an orphan — and step 4 returns `DRAINING`; if this statement committed first,
  T2's guard (whose fresh clock sample follows a committed writer, §3) sees the expired deadline and
  returns `DEADLINE_EXCEEDED` without writing.
- **D-D preserved.** This changes only node rows; run status is still set by T4,
  which decides the deadline atomically, so the run becomes `timed_out` whenever
  deadline confirmation precedes a successful T4.
- **Gaps between statements are safe.** If the deadline passes between this
  statement and T4 (the statement saw "not expired"), orphans remain `running`,
  T4's `NOT EXISTS` refuses, the transaction rolls back (`NOT_FINALIZED`), and the
  next attempt resolves them. A terminal run can never hold a `running` row.
- **Skipped for `natural = 'succeeded'`.** A genuinely succeeded run has no pending
  retry or orphan; if one is present it is an inconsistency, and leaving it
  untouched makes T4 refuse so the bug surfaces instead of being resolved away.

**When `finalize_run()` is called.** On deadline confirmation the loop calls it
**immediately** with `natural = 'timed_out'`: orphans and pending retries are
resolved at once — no wait for another lease expiry — and the call returns
`DRAINING` while any current-epoch attempt is live; the loop calls it again as each
drain step completes (a draining attempt may itself produce a new `retry_wait`
row), until it returns `FINALIZED`. For cancellation and failure it is called once
the loop's own tasks are done.

**Commit semantics.** When T4 executes, steps 2–3 and T4 commit **together or not
at all**: no committed state shows a terminal run with an orphan or a pending
retry, nor a resolution on a run that failed to finalize. When step 5 returns
`DRAINING` the transaction commits steps 2–3 on their own (it does not roll back):
each is individually fenced and idempotent, and each writes only rows that can no
longer become live — older-epoch orphans after a confirmed deadline, and
`retry_wait` rows that will never be retried.

The pending-retry statement:

```sql
-- RESOLVE_PENDING_RETRIES_SQL (finalize_run step 3)
UPDATE node_runs SET
       status   = CASE WHEN effect_class = 'unsafe_write' AND outcome = 'unknown'
                       THEN 'failed' ELSE 'cancelled' END,
       retry_at = NULL
       -- outcome, error, output, attempt, failures, started_at, effect_class,
       -- started_epoch are deliberately NOT in the SET list.
 WHERE run_id = :run_id AND status = 'retry_wait'
RETURNING node_key, status, outcome, effect_class, attempt;
```

**Invariant INV-U (D-E, D-F, D-G, D-I).** *No cancellation, deadline, retry
suppression, or terminal-run transition may convert an already-unknown external
outcome into a known outcome without new evidence.* "New evidence" means exactly
one thing: a later attempt's own definitive result — a confirmed success or a
definitive, no-longer-ambiguous failure — written by T3 (architecture §6.2
rules 4 and 5). The two resolution statements enforce INV-U **structurally**:
the pending-retry statement has no `outcome` in its `SET` list, so it cannot change
it in either direction — it neither upgrades `unknown` to `known` nor invents doubt
where none was recorded; the orphan statement (D-I) may set `outcome` only to
`unknown`, and only for `idempotent_write`/`unsafe_write` rows whose attempt was
started without a result — it adds the doubt the Run-deadline matrix requires and
can never write `known`. A database trigger was considered and not adopted: "new evidence" is a
runtime fact (a later attempt's definitive result), not something a row-level
trigger can distinguish from an illegitimate rewrite without additional state.
INV-U is instead covered by tests over every path (§9, M2.6).

The decision uses only persisted evidence — the row's `effect_class` (immutable,
§5.2) and its recorded `outcome` — and no row is assumed to share another's
uncertainty state:

| `effect_class` | recorded `outcome` | Why such a row exists | Resolved to |
|---|---|---|---|
| `pure` | known | ordinary failure or node timeout, retryable | `cancelled`, known |
| `read` | known | same | `cancelled`, known |
| `idempotent_write` | known | definitive failure, retry pending | `cancelled`, known |
| `idempotent_write` | **unknown** | unknown-outcome node timeout with retry budget left (§6.2 dedicated rule) | `cancelled`, **unknown** |
| `unsafe_write` | known | a retry is scheduled only after a provably pre-dispatch failure or a not-dispatched timeout | `cancelled`, known |
| `unsafe_write` | **unknown** | cannot occur: unknown ⇒ `failed`/`outcome_unknown`, never `retry_wait` (§6.2 rule 1) | `failed`, **unknown** — never `cancelled`; report `engine_inconsistency` |
| `pure` / `read` | **unknown** | cannot occur (they mutate nothing external) | `cancelled`, unknown preserved; report `engine_inconsistency` |

**What `cancelled` here does and does not mean.** The retry was *suppressed*; it
was never executed. The row keeps its `attempt` and `failures` (no new attempt
was started), its `started_at`, and the previous attempt's recorded `error` and
`output`, so the node's **original failure is preserved** and nothing implies the
pending retry ran. The suppression is recorded in the `run_events` warning, not by
overwriting `error`. The `idempotent_write` + known row stays known although the
§6.2 Run-deadline column says `cancelled`, **unknown** for that class: that cell
describes an attempt *in flight* when the deadline hits, whereas a `retry_wait`
row's last attempt already has a recorded result and nothing is in flight. The
`idempotent_write` + unknown row is exactly the Run-deadline/Cancel cell.

**Where `finalize_run()` applies, and which decision covers each path:**

| Path | `natural` | `reason` | Covered by |
|---|---|---|---|
| Drain to run deadline; a claimer's post-claim check 2, including a parked run woken at `deadline_at` by its `LEAST(...)` `visible_at` | `timed_out` | run deadline confirmed | D-E (approved) |
| Cancellation of a *waiting* run, resolved by the next claimant | `cancelled` | run cancelled | D-F (approved) |
| Cancellation of a *running* run, after the U5 drain | `cancelled` | run cancelled | D-F (approved) |
| A run ending `failed` while a sibling node is in `retry_wait` | `failed` | run failing | D-G (approved) |
| A run ending `succeeded` | `succeeded` | — | none can exist (a `retry_wait` row means a node is not terminal) |

**D-G specifically.** A terminal `failed` run never retains `retry_wait` rows. The
sibling's retry is suppressed and the pending node resolved by the same statement
and table above (`cancelled`, outcome and uncertainty preserved, never
`unknown` → known, its own last failure retained), while the **run's `failed`
status is unchanged by it**: that status comes from `:natural = 'failed'` in T4,
and the failing node's own row is untouched. (If the deadline is confirmed before
T4, D-D still applies and the run is `timed_out`; the resolution does not change
that precedence.) Because the statement never touches `outcome`, an unknown
`idempotent_write` sibling stays `unknown`, `has_unknown_outcome` stays true, and
the run ends `failed` with every node row terminal.

**D-F specifically.** An `idempotent_write` row in `retry_wait` with unknown
outcome may become `cancelled` by cancellation (or deadline), but its outcome
stays `unknown`. Architecture §6.2a, for a claimed *waiting* run, now says the same:
it resolves any `retry_wait` rows as `cancelled`, keeping each row's recorded
outcome (an unknown outcome stays unknown), last failure, and attempt count. The
source and this design therefore agree, and agree with §6.2's rule that an unknown
outcome is never reported as known and with the matrix's `idempotent_write` Cancel
cell (`cancelled`, **unknown**).

### 4.11 Graceful shutdown (SIGTERM): grace-period expiry (D-C)

Adopted: **crash-recovery semantics**. SIGTERM is **not** run-deadline expiry and
introduces **no new interruption cause**; no node result is fabricated.

1. **Stop claiming** new runs.
2. **In-flight attempts continue** during the existing grace period (no new
   parameter) and the results of attempts that finish normally are persisted by
   `finish_node()` (§4.4) as usual.
3. **At grace expiry, per owned run:** if no live attempt remains, park it
   (`visible_at = now()`) so another worker continues immediately. If an attempt
   is **still running**, park the run **without writing any node row**: the row
   stays `running` with its original `started_epoch`, `attempt`, `failures`
   unchanged, and nothing is awaited further — the process then exits, which ends
   those tasks.
4. **On the next claim** — by any worker, via ordinary T1 with
   `prev_status = 'waiting'` — `lease_epoch` becomes E+1, so the row with
   `started_epoch = E` is an **orphan** (architecture §3.1: "its owner is gone";
   ADR-0004: orphans are keyed on `started_epoch` vs `lease_epoch` only). The
   orphan is resolved by the existing §6.2 **Crash / lease-lost** column: `pure`
   and `read` re-execute (T2's orphan edge, `attempt + 1`); `idempotent_write`
   re-executes with the same idempotency key; `unsafe_write` is `failed`,
   `outcome_unknown`, unknown (a crash can never prove non-dispatch) and the run
   fails ignoring `on_error`. The old worker's knowledge that it had or had not
   dispatched is deliberately **not** used — that is what "crash semantics" means.
   `recovery_count` is **not** incremented (the claim is from `waiting`) and no
   "reclaimed" event is written, consistent with ADR-0003 ("parking and retries
   don't trip the poison guard").
5. **Precedence at that next claim** is decided by the run's state then, never by
   SIGTERM: an expired deadline ⇒ post-claim check 2 first (orphans by the
   Run-deadline column, `retry_wait` rows by §4.10, `timed_out`); a pending cancel
   ⇒ §6.2's combined reclaimer-plus-cancel rule.

**Is the existing park operation safe for this?** Checked against the §4.5 SQL:

| Park element | Verdict for grace-expiry parking |
|---|---|
| Fencing (`status='running'`, owner, epoch) | Required and sufficient: only the current holder can park |
| "No in-flight tasks" | Worker-side prose, **not in the SQL** (§4.5 above); graceful release deliberately parks with live attempts — no SQL change |
| `lease_owner = NULL` with `status = 'waiting'` | Satisfies `lease_owner_matches_status` |
| `lease_epoch` unchanged | Correct: the next claim increments it, which is what creates the orphan |
| `visible_at = LEAST(min(retry_at), deadline_at)` | **Does not fit**: architecture §4.5 specifies `visible_at = now()` for graceful release, so another worker picks the run up at once. This is the architecture's own value, not a new one |
| `AND cancel_requested_at IS NULL` | **Blocks it when a cancel is pending** (0 rows), so graceful release uses the dedicated statement below; the ordinary park keeps it |

The graceful-release park (D-H, **approved**) is a **dedicated statement**, not a
flag on the ordinary park:

```sql
-- park_for_shutdown(): graceful-release park (SIGTERM). Same fencing and epoch
-- transition as ordinary park; visible_at = now(); NO cancel predicate.
UPDATE runs SET status = 'waiting', lease_owner = NULL, visible_at = now()
 WHERE id = :id AND status = 'running'
   AND lease_owner = :worker AND lease_epoch = :epoch
RETURNING status;
```

It lives in its own function (`park_for_shutdown()`), never as an optional
parameter of the ordinary park, so the ordinary park **keeps** both its
`cancel_requested_at IS NULL` predicate and its `LEAST(min(retry_at),
deadline_at)` wake time — the preconditions of unrelated park operations are not
weakened, and a regression test pins that (§9, M2.4).

**Why dropping the cancel predicate here is safe.**

1. *What the predicate protects.* In the ordinary park it stops a pending cancel
   from sleeping until a **future** `visible_at` (the run would otherwise be
   parked until the next retry time or deadline). With `visible_at = now()` that
   hazard cannot occur: the run is claimable immediately.
2. *Nothing is lost.* `cancel_requested_at` is sticky (`COALESCE` in the API
   statement) and unchanged by the park, so the next claimant reads it from its
   own T1 `RETURNING` and takes post-claim check 4 — exactly as for the API
   cancel of a `waiting` run (§6.2a).
3. *Resolved under the new lease.* A pending cancellation is resolved by the next
   claimant under its newly acquired epoch, never by the exiting worker: node
   rows left `running` by the park are orphans (`started_epoch` older than the new
   epoch) and follow §6.2's reclaimer-plus-cancel rule — `pure`/`read` resolve
   `cancelled` with no re-execute, `idempotent_write` resolves `cancelled`,
   **unknown**, `unsafe_write` follows the Crash column (`failed`,
   `outcome_unknown`) — then `finalize_run()` (§4.10) finalizes `cancelled`
   (or `timed_out` if the deadline has meanwhile expired, check 2 first).
4. *Fencing is unchanged.* The statement keeps `status = 'running' AND
   lease_owner = :worker AND lease_epoch = :epoch`, leaves `lease_epoch`
   untouched, and sets `lease_owner = NULL` with `status = 'waiting'`
   (satisfying `lease_owner_matches_status`). The next claim increments the epoch.
5. *Immediate reclaim.* `visible_at = now()` satisfies T1's `visible_at <= now()`
   as soon as the park commits, so any other worker can claim at once without
   waiting for the lease TTL. The exiting worker has stopped claiming (step 1), so
   it will not reclaim its own run.

The park runs as one transaction — fenced guard, one informational `warning`
event through the proof ("graceful shutdown: attempt(s) still running at grace
expiry; run parked; node row(s) left for orphan recovery"), then
`park_for_shutdown()`; 0 rows rolls the event back.

**The old holder cannot write after ownership has moved.** Once the park commits
the run is `waiting` with `lease_owner = NULL`; any later write by the old process
fails its fenced guard (`status = 'running'` no longer holds), including its
heartbeat and any late T3 from a still-running task. After another worker claims
(`status = 'running'`, epoch E+1) the same writes fail the epoch check. Those
tasks may complete externally before the process exits; that is exactly the
crash-recovery case (orphan resolved by the Crash column, same idempotency key for
`idempotent_write`), not something this design hides.

**Overlap limitation (retained, not eliminated).** After a graceful-release park
the old process may keep running an already-started attempt task until it exits,
while a new lease holder is already recovering the run — resolving the orphan
(Crash column, or the Run-deadline column under D-I) or re-executing it. Fencing
prevents the old process's stale **database** writes; it cannot undo, prevent, or
disprove an **external** side effect that process already dispatched or dispatches
before exiting. This design therefore never claims the overlap is impossible: the
same-key idempotency contract stays necessary (`idempotent_write` re-execution
reuses the key; `pure`/`read` are harmless to duplicate; `unsafe_write` is already
recorded `unknown`), and a fenced-out worker is never treated as proof that its
operation did not execute.

**Does T1's orphan-recovery path handle it?** T1 itself only claims; orphans are
resolved by the step that runs after the claim, keyed on `started_epoch <
lease_epoch`, independent of `prev_status` (ADR-0004). The M2.5 loop therefore
**must run orphan resolution after every claim, including `prev_status =
'waiting'`** — not only on lease-expiry takeovers; this is tested explicitly
(§9, M2.5).

## 5. `run_events` sequencing and isolation

- **Isolation level: READ COMMITTED**, the architecture's own already-stated
  assumption (`docs/architecture.md` §4) — not a new assumption introduced here.
- **Every event writer acquires the parent `runs` row lock first**, by
  construction: T1/T2/T3/heartbeat/park/T4 all *are* a claim or fenced-guard
  `UPDATE` before any `run_events` insert in the same transaction; the API's
  cancel statement never calls `append_event()` at all (section 4.6).
- **Why `MAX(seq) + 1` sees the preceding committed event:** not READ COMMITTED
  alone, and not the lock alone — the combination. READ COMMITTED guarantees each
  *statement* sees data committed as of that statement's start; the row lock
  guarantees a second transaction's lock-acquiring statement cannot even begin
  until the first has committed and released it. By the time the second
  transaction's `MAX(seq)` read executes, the first's insert is already
  committed and visible.
- **`append_event()`'s contract requires a `LeaseProof`** obtained from
  `run_fenced_guard()`/`claim_run()` in the *same* transaction — never a bare
  row lock with no owner/epoch verification behind it (see section 3's
  `LeaseProof` docstring for the disclosed limitation this still carries).

## 6. Orphan-reclaim domain extension (M1 → M2 seam)

`domain.node_run.NodeRun` gains one field, and `start_attempt()` gains one new
legal transition — both additive, both backward-compatible with M1's existing
208 tests:

```python
@dataclass(frozen=True)
class NodeRun:
    ...
    started_epoch: Optional[int] = None   # NEW


def start_attempt(
    existing: Optional[NodeRun], *, run_id: str, node_key: str,
    resolved_effect_class: EffectClass,
    current_lease_epoch: Optional[int] = None,   # NEW, additive, default None
) -> tuple[NodeRun, bool]:
    ...
    if existing is not None and existing.status is NodeRunStatus.RUNNING:
        if current_lease_epoch is None:
            raise ValueError(
                "restarting a 'running' node_run requires current_lease_epoch "
                "so this function can verify the orphan condition itself"
            )
        if existing.started_epoch is None or existing.started_epoch >= current_lease_epoch:
            raise ValueError(
                f"(run_id={run_id!r}, node_key={node_key!r}) is not an orphan: "
                f"started_epoch={existing.started_epoch!r} is not older than "
                f"current_lease_epoch={current_lease_epoch!r} -- refusing to "
                f"restart a live attempt"
            )
        # Orphan condition verified by this function, not asserted by the
        # caller -- the only input is the worker's own real, just-claimed
        # epoch (see ClaimedRun, section 3), never a trust-me boolean.
        ...
```

A caller cannot restart a live node by lying, because there is nothing to lie
about: the only input is `current_lease_epoch`, sourced from the worker's own
`ClaimedRun` (itself sourced only from a real T1 `RETURNING`), and the function
itself rejects any value that doesn't exceed the stored `started_epoch`. The two
existing M1-legal edges (`absent → running`, `retry_wait → running`) are
untouched.

## 8. Race-condition matrix (consolidated)

| # | Race | Outcome |
|---|---|---|
| 1 | Cancel commits before T4(`succeeded`) | T4's `CASE` observes the flag → `cancelled` |
| 2 | T4 commits before cancel | Cancel's predicate fails → `409`, already-final status returned |
| 3 | Cancel vs. park | Park requires `cancel_requested_at IS NULL`; whichever wins, the other's predicate correctly fails |
| 4 | Cancel of `queued` vs. concurrent claim | `SKIP LOCKED` + re-checked predicate: exactly one side wins |
| 5 | A zombie's T4 vs. a reclaimer | Epoch mismatch ⇒ 0 rows ⇒ refused |
| 6 | Reclaim vs. a delayed heartbeat | Row locks serialize; the epoch guard decides |
| 7 | Two workers' claim queries fire simultaneously | `FOR UPDATE SKIP LOCKED` guarantees exactly one acquires the lock |
| 8 | `idempotent_write` timeout exhaustion vs. a concurrent cancel | `:natural='failed'` has top precedence in T4's `CASE`; wins regardless of arrival order |
| 9 | Reclaimer finds an orphan **and** `cancel_requested_at` already set | §6.2's own combined rule; the reclaimer's resolution pass records the event under its own fresh proof |
| 10 | Graceful SIGTERM park races a concurrent claim | Park is itself fenced; 0 rows if superseded |
| 11 | Current worker's heartbeat renewal vs. another's T1 reclaim, no prior reclaim yet | Whichever acquires the row lock first wins outright; never a double-owner outcome |
| 12 | A worker holding a stale epoch attempts T2/T3 after another has reclaimed | Fenced guard's epoch check matches 0 rows ⇒ refused before any `node_runs` write |
| 13 | A buggy/duplicate T2 call against an already-terminal `node_runs` row | T2's restricted `WHERE` (section 4.3) matches neither branch ⇒ 0 rows ⇒ `engine_inconsistency` |
| 14 | T2 against a `running` row that is **not** actually orphaned | Same rejection as #13 |
| 15 | Two concurrent event writers for the same `run_id` | Serialized by the shared `runs` row lock; `MAX(seq)+1` sees the prior commit; no duplicate `seq` possible |
| 16 | API cancellation racing with T2 for the same run | Both statements contend for the same `runs` row lock, so exactly one goes first. **Cancel locks first and commits:** T2's fenced guard (which blocks until the cancel's transaction ends, then evaluates its `WHERE` against the committed row) returns `cancel_requested_at`, `start_node()` returns `CANCELLED`, and the prospective node is never started. **T2 locks first:** its node-start transaction (guard, `node_runs` upsert, event) may commit before the cancel; the cancel then sets only the flag, that node is now in flight and drains naturally under U5 (§6.2a/ADR-0009) — it is neither killed nor rewritten. No double ownership is possible (the cancel statement never touches `lease_owner`/`lease_epoch` or `node_runs`), and no unfenced write occurs on either ordering (the API writes only `runs.cancel_requested_at`; every `node_runs`/`run_events` write stays inside the fenced T2 transaction) |
| 17 | Run-deadline expiration racing with T2 | T2 evaluates the deadline against `guard.db_now`, the database timestamp returned by the same fenced `UPDATE` — never the worker's clock — so there is no local-clock skew window. If `deadline_at <= db_now` at that statement, `start_node()` returns `DEADLINE_EXCEEDED`: no new node starts and the run enters deadline resolution, finalizing `timed_out`. This holds **even if cancellation is also requested** (deadline is checked first, §4.3), preserving `timed_out` precedence over `cancelled` per §6.2a/ADR-0009. If the deadline expires only after T2's guard has already succeeded, the node was legitimately started before expiry and becomes in flight; the expiry is then observed through the live worker's deadline wait and a fresh fenced guard (§4.8) — never from the local timer alone — or, failing that, by the next heartbeat/T3 guard |
| 18 | A node's late result racing the interruption resolution (cancel or node timeout) of the **same attempt** *(under Option B the run deadline interrupts no live attempt, so it is not a source of such resolutions)* | Both are T3-shaped writes behind the same fenced guard, so they serialize on the `runs` row lock; both carry `status = 'running' AND started_epoch = :epoch AND attempt = :attempt` (§4.4). The first to commit wins; the second matches 0 rows. A result that commits first means the attempt was never interrupted (§6.2 definition); a resolution that commits first makes the late result `RESULT_DISCARDED` — never an overwrite |
| 19 | A stale result from attempt N arriving after attempt N+1 started in the **same** epoch (e.g. node-timeout ⇒ `retry_wait` ⇒ retried while attempt N's task is still alive) | `status = 'running' AND started_epoch = :epoch` alone would match attempt N+1's row; `AND attempt = :attempt` makes the stale write match 0 rows ⇒ `RESULT_DISCARDED` |
| 20 | A legitimate result arriving after `visible_at` has elapsed with no reclaim | Accepted: the fenced guard matches on owner+epoch only (no `visible_at` condition), renews `visible_at` as a side effect, and the node `UPDATE` then applies. If another worker *had* reclaimed, the guard matches 0 rows ⇒ `LEASE_LOST`, the result is abandoned and the node is an orphan for the new owner |
| 21 | Run deadline confirmed while live attempts are still running (the drain) | The worker stops starting nodes (T2 refuses with `DEADLINE_EXCEEDED`, and the loop stops proposing starts) but does not interrupt anything: each live attempt's result persists through `finish_node()` under the unchanged §4.4 predicate, a result racing the deadline confirmation is simply persisted if the node is still `running`, and T4 (`:natural = 'timed_out'`) is issued only after every live attempt is resolved. No new node row is created after confirmation, and no node row with a live attempt is overwritten |
| 22 | The draining worker crashes or loses its lease mid-drain | Its further writes fail the fenced guard (0 rows); after lease expiry a claimer's post-claim check 2 resolves the orphans by the Run-deadline column (never re-executing them), then finalizes `timed_out`; an orphan `unsafe_write` is `failed`/`outcome_unknown`/unknown because a crash can never prove non-dispatch |
| 23 | T4 evaluates before `deadline_at` | The normal result stands (terms 2–4 of §4.5: `succeeded`/`failed`/`cancelled`); a deadline that passes afterwards finds a terminal run (fenced guard 0 rows) and does nothing |
| 24 | T4 evaluates at/after `deadline_at` without the loop having confirmed it (all nodes succeeded; or some failed; or a cancel is pending) | Term (1) ⇒ `timed_out`, decided on database time against the locked row; node rows untouched, `has_unknown_outcome` derived from them; never `failed`/`cancelled` |
| 25 | The deadline passes while a competing writer holds the `runs` lock and `finalize_run()` waits | The guard (statement 1) blocks until the lock is granted; T4 (statement 2) then executes with that lock already held, so its single clock sample is taken after the lock ⇒ `timed_out`. With `now()` the decision would have used the earlier transaction start and could have finalized the normal result. This holds for a blocker that modifies the row **and** for a lock-only blocker released without modification, because T4's sample follows the guard's lock acquisition either way |
| 26 | T4 attempted while a node row is `running` or `retry_wait` (live attempt, unresolved orphan, or leftover retry) | `NOT EXISTS` predicate ⇒ 0 rows; a fresh fenced guard distinguishes lease lost from unresolved nodes; leftover `retry_wait` is resolved (§4.10) and T4 retried once; a remaining `running` row is left for lease expiry and orphan recovery |
| 27 | SIGTERM park vs. a late T3 or heartbeat from the old holder | After the park the run is `waiting` ⇒ `status = 'running'` fails ⇒ 0 rows; after another worker claims, the epoch check fails ⇒ 0 rows; the old holder can never write once ownership has moved |
| 28 | SIGTERM park vs. a concurrent or already-pending API cancel | `park_for_shutdown()` (D-H) has no cancel predicate and sets `visible_at = now()`: it succeeds whichever order the cancel lands in; the flag is sticky, the run is claimable at once, and the next claimant observes it (post-claim check 4) and resolves under its own lease. The *ordinary* park still returns 0 rows when a cancel is pending |
| 29 | A SIGTERM-parked run whose deadline expires, or which receives a cancel, before it is next claimed | The next claimer's post-claim checks decide: check 2 (Run-deadline column for orphans, §4.10 for `retry_wait`, `timed_out`) precedes check 4; SIGTERM is never itself the cause |
| 30 | Immediate reclaim after a SIGTERM park, while the old process still has attempt tasks running | `visible_at = now()` makes the run claimable at once; the new claim bumps the epoch, so the old holder's guard, heartbeat, and any T3 fail (§8 row 27); the left-behind `running` node rows are orphans resolved by the Crash column (same idempotency key for `idempotent_write`); no `recovery_count` increment |
| 31 | A failed run (T4 `:natural = 'failed'`) with a sibling node in `retry_wait` (including an unknown-outcome `idempotent_write`) | `finalize_run()` resolves the sibling in the same transaction as T4 (§4.10): `cancelled`, outcome preserved, own failure retained; the run is `failed`; if T4 is refused the resolution rolls back with it; no terminal run ever holds a `retry_wait` row |
| 32 | An unknown-outcome `idempotent_write` `retry_wait` row meets cancellation, deadline, or a failing run | Every path uses the §4.10 statement, whose `SET` list excludes `outcome`: the row may become `cancelled` but stays `unknown` (INV-U); `has_unknown_outcome` stays true |
| 33 | Deadline confirmed by the current holder while an orphan (older epoch) still awaits re-execution | `finalize_run()` step 2 resolves it immediately, in the same fenced transaction, by the Run-deadline column — no wait for lease expiry; T2 would refuse to restart it anyway. The run reaches `timed_out` in the same call once nothing live remains |
| 34 | A current-epoch live attempt exists when `finalize_run()` runs | Step 2 skips it (`started_epoch` equals the epoch, not older) and step 4 counts it ⇒ `DRAINING`: no T4, steps 2–3 commit, the attempt drains normally; T4 only after its T3/resolution commits (T4's `NOT EXISTS` is the database backstop) |
| 35 | A late T3 racing orphan resolution | Only the old holder could write an orphan row, and its T3 either committed before the new claim (row no longer `running` ⇒ the orphan statement skips it) or starts after it and fails its guard on the epoch (⇒ `LEASE_LOST`); the current holder's own T3 requires `started_epoch = :epoch` and cannot match an orphan. A committed T3 result is never overwritten |
| 36 | The old lease holder writes after the new lease has resolved its orphan | Guard epoch check ⇒ 0 rows ⇒ `LEASE_LOST`; the resolved row is unchanged; the old process's external effect, if any, is not undone (overlap limitation, §4.11) |
| 37 | T2 restart of an orphan racing deadline-orphan resolution | They serialize on the `runs` lock. T2 first ⇒ the row is now a live current-epoch attempt (not an orphan), step 4 ⇒ `DRAINING`. Resolution first ⇒ T2's guard (its fresh clock sample follows the committed writer, §3) sees the expired deadline, returns `DEADLINE_EXCEEDED`, writes nothing |
| 38 | The deadline passes between the orphan statement and T4 | The orphan statement saw "not expired" and resolved nothing; T4's `NOT EXISTS` refuses the still-`running` orphan ⇒ rollback ⇒ `NOT_FINALIZED`; the next call resolves it. No terminal run ever holds a `running` row |
| 39 | SIGTERM-parked run's old process still runs a task while a new holder resolves its orphan at the deadline | Fencing blocks all stale database writes; the external side effect cannot be undone and overlap is possible; outcome stays `unknown` for write classes and the same-key contract applies (§4.11) |
| 40 | T4's deadline decision and `finished_at` come from one clock sample | A single materialized sample `s.t` feeds both: for every outcome with `:natural` not itself `'timed_out'`, `(status = 'timed_out') ⇔ (finished_at >= deadline_at)`. A deadline that falls between what would have been two independent clock calls cannot yield `timed_out` with `finished_at < deadline_at`, nor a normal status with `finished_at >= deadline_at` |
| 41 | T4 attempted outside a transaction whose fenced guard succeeded | `run_t4()` calls `_check_proof()` and refuses before any SQL: the single sample is never taken unless the `runs` lock is already held |
| 42 | A guard waits behind another writer of the `runs` row | The renewal is stamped from a fresh `clock_timestamp()` sample, not the transaction start: behind a writer that committed a new row version the sample is post-wait and `visible_at = db_now + ttl` is one instant; behind a lock-only holder released without modification the sample may predate the wait by at most `W`, in the conservative (earlier-expiry) direction; the guard's `WHERE` is unchanged (no `visible_at`), so ownership is decided only by owner and epoch |

## 10. Disclosed limitations (not blocking, stated for the record)

- Python 3.14 execution verification remains the open item carried from M1 — no
  new dependency introduced by this design changes that status.
- `run_events`'s protection via `LeaseProof` is an in-process correctness guard,
  not a security boundary (section 3) — accepted given M2's threat model (no
  adversarial/arbitrary code execution anywhere in this project).
- Python cannot preempt or kill a running coroutine or thread (§4.9): a node
  that blocks the event loop delays node-timeout enforcement, the §4.8 deadline
  timer, and the §4.9 drain until it yields. State stays safe (fenced writes,
  the heartbeat on its own thread), but run-deadline and node-timeout timeliness
  for a misbehaving first-party node is bounded only by payload/expression caps
  and the RB6 stress test, not guaranteed. No subprocess architecture is
  introduced to change this.
- **SIGTERM overlap (retained, §4.11):** after a graceful-release park the old
  process may keep running an already-started task while a new holder recovers
  the run. Fencing stops its stale database writes but cannot undo, prevent, or
  disprove an external side effect already dispatched; overlap is possible, and
  the same-key idempotency contract remains necessary.
- The `postgres` image used by `testcontainers-python` locally and by the
  GitHub Actions `services:` block in CI must both be digest-pinned per the
  project's existing no-floating-tags discipline (ADR-0015) when M2.3 actually
  introduces them. Neither mechanism introduces a Dockerfile or Compose file
  into the repository (see D3, section 1) — there is no Compose artifact of
  any kind before M4.

### Decision record

**Specified at design level (no product decision involved):** the T3 atomic
persistence predicate, zero-row handling, and the rule that a result in hand is
accepted while the node is still `running` (§4.4); race rows 18–20; tests (k)–(o).
`attempt = :attempt` goes beyond the minimum conditions requested, for the reason
given in §4.4.

**D-A — Live nodes at confirmed run-deadline expiry: RESOLVED, Option B
(approved).** No new starts; live attempts are not interrupted by the deadline;
they finish and persist under the fenced guard and §4.4 predicate; abnormal ends
follow the existing node-timeout/crash rules; `timed_out` only after every live
attempt is resolved; unknown outcomes preserved (§4.8 item 3, §4.9). The source text now states it explicitly (architecture §4.6 and §6.2, source
change 2 below), consistent with ADR-0009's U5 rationale.
Accepted consequence: the run can overrun `deadline_at` by up to the longest live
attempt's remaining per-node timeout (default 5 min). Option A's parameters
(`interrupt_grace_s`, `abandon_hard_limit_s`, `max_abandoned_attempts`), the
abandoned-task set, and its tests are absent from this document.

**D-D — Run failure versus run deadline: RESOLVED (approved).** T4 decides the
deadline atomically, in-statement, on one shared `clock_timestamp()` sample
(§4.5): T4 before the deadline ⇒ the normal result; T4 at/after it ⇒ `timed_out`
even if nodes failed or a cancel is pending; node failures and `outcome_unknown`
are never rewritten. Race rows 23–26. Follows from this precedence: a run whose
nodes all succeeded but whose T4 lands at/after `deadline_at` is `timed_out`
(nodes stay `succeeded`).

**D-E, D-F, D-G — Pending retries at finalization: RESOLVED (approved)** (§4.10).
One routine, `finalize_run()`, resolves every `retry_wait` row and runs T4 in a
single all-or-nothing transaction (with the `DRAINING` nuance of D-I below), for every path: deadline, cancellation (running
or waiting run), and failure. The statement's `SET` list excludes `outcome`, so
INV-U holds structurally: *no cancellation, deadline, retry suppression, or
terminal-run transition converts an unknown external outcome into a known one
without new evidence.* An unknown `idempotent_write` `retry_wait` row becomes
`cancelled` with outcome `unknown`; a failed run's sibling `retry_wait` rows are
resolved `cancelled` with outcome and uncertainty preserved, the sibling's own last
failure retained and the run's `failed` status unchanged. No terminal run can hold
a `running` or `retry_wait` node row (T4's `NOT EXISTS` predicate).

**D-C and D-H — SIGTERM grace expiry and the graceful-release park: RESOLVED
(approved)** (§4.11). Crash-recovery semantics: nothing fabricated; the run is
parked by the dedicated `park_for_shutdown()` statement (`visible_at = now()`, no
cancel predicate, same fencing and epoch transition); the node row is left
`running` with its original `started_epoch`; the next claim makes it an orphan
resolved by the existing Crash/lease-lost column; a pending cancellation is
resolved by that next claimant under its new lease; `recovery_count` is not
incremented; no new interruption cause; SIGTERM is not equated with the deadline.
The ordinary park keeps its `cancel_requested_at IS NULL` predicate and
`LEAST(...)` wake time.

**Guard timestamp and renewal: RESOLVED (approved, revised)** (§3). `run_fenced_guard()` renews with `visible_at = clock_timestamp() + :ttl` and returns `db_now` as `visible_at - :ttl` — the same single sample — so a guard that waited on the row lock no longer stamps a stale transaction-start expiry. The authorization predicate still has no `visible_at`; T1's `now() + :ttl` (T1 never waits) and T2's conservative `retry_at <= now()` are unchanged. T4 still decides the deadline itself and no Python-side value can replace it; no lease validity decision rests on `visible_at > now()` alone.

**T4 single sample: RESOLVED** (§4.5). One materialized sample `s.t` feeds both the deadline comparison and `finished_at`, so status and `finished_at` can never straddle the deadline. The sample is taken after the row lock **by statement order**: T4 runs only through `run_t4()`, which requires the same-transaction `LeaseProof`, i.e. after the guard's lock. The self-locking CTE chain you described was analysed and **not adopted as the guarantee** — see the first flag below.

**D-I — Orphans awaiting re-execution at the deadline: RESOLVED (approved)** (§4.10). When the current holder confirms the deadline, `finalize_run()` resolves `running` rows with `started_epoch < lease_epoch` by the existing Run-deadline matrix in the same fenced transaction, in the specified order (guard; orphans; `retry_wait`; count current-epoch live rows; `DRAINING` without T4 if any, else T4; commit together), with no wait for another lease expiry. The statement re-checks the fence and DB-confirmed expiry itself, resolves only strictly older-epoch rows still `running` (so it cannot overwrite a committed T3 result or touch a live attempt), never writes `outcome = 'known'`, never re-executes, and treats a fenced-out old worker as no evidence of non-execution. D-D is preserved: run status comes only from T4's atomic deadline term.

### Remaining items — interpretation flags, not open product decisions

No product decision is open. These record readings or hardenings of this document,
stated so they can be vetoed:

- **The in-statement lock-then-sample CTE chain was not adopted.** PostgreSQL's
  documentation says the WITH queries and the main query are "notionally executed at
  the same time", orders nothing between a CTE and a row lock, and does not say when
  target-list or `SET` expressions are evaluated relative to a lock. T4's lock-first
  guarantee comes from a documented property (row locks held to transaction end)
  plus statement order inside `finalize_run()` and the `run_t4()` proof check; T4 is
  therefore not self-locking and standalone use is unsupported (§8 row 41). Pinned by
  real-PostgreSQL tests (r), (mm), (cc).
- **`ClaimedRun.prev_status` replaces `claim_db_now`.** Post-claim check 1 needs the
  run's pre-claim status; checks 1–2 read the first fenced guard's `db_now`, so no
  claim-time timestamp is stored.
- **Guard `db_now` is derived as `visible_at − :ttl`**, one sample for renewal and
  reading. Behind a lock-only blocker released without modification the sample may
  predate the wait by at most the wait (earlier expiry, conservative); freshness behind
  a *modifying* blocker is pinned by test (cc), not by documentation.
- **`DRAINING` commits steps 2–3 of `finalize_run()`.** "Commit all changes together"
  applies to the T4 path; when step 5 returns `DRAINING` the already-fenced, idempotent
  resolutions commit instead of rolling back.
- **`natural = 'succeeded'` skips steps 2–3**, so a stray orphan or `retry_wait` row
  makes T4 refuse and surfaces as an inconsistency.
- **Database clock step (Risk R8, documented-not-solved):** if the clock stepped
  backwards after the loop confirmed expiry, the orphan statement would resolve
  nothing, T4 would refuse (`NOT_FINALIZED`), and recovery would fall back to lease
  expiry and the next claimer's check 2.
- **SIGTERM overlap is retained, not eliminated** (§4.11, §10): fencing stops stale
  database writes but cannot undo an external side effect, so the same-key idempotency
  contract remains necessary.

Approval to begin M2.1 is the user's call, not this document's.
